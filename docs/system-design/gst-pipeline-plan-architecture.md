# Организация GST-пайплайнов: от набора флагов к разрешённому плану

Статус: **проект**. Ничего из описанного здесь не реализовано; документ фиксирует диагноз,
целевую модель и порядок перехода. Реализация — отдельными шагами, см.
[«Миграция»](#миграция-каждый-шаг-отгружаем).

Связанные документы: [точность перемотки](gstreamer-seek-accuracy.md) (что уже починено и какой
ценой), [устойчивость пайплайна](gstreamer-pipeline-robustness.md),
[capability-aware playback](torrent-mod-playback-capability-fallback-backlog.md) (откуда придёт
профиль клиента), [ADR-0003](../adr/0003-no-global-player-patching.md).

## 1. Диагноз

Решение «как проигрывать этот файл» **нигде не представлено как значение**. Оно
переоткрывается из пары `(Config, ProbeInfo)` в семи местах, у каждого свой `switch`:

| # | Место | Что решает |
|---|---|---|
| 1 | `validateProbe` (`service.go`) | можно ли вообще играть |
| 2 | `shouldUseCueTimeline` (`service.go`) | читать ли индекс Matroska |
| 3 | `videoIsTranscoded` (`task.go`) | копировать или перекодировать |
| 4 | `Task.seekCanBeAccurate` (`task.go`) | просить ли `ACCURATE` |
| 5 | `createPipelineArgs` (`pipeline_gst.go`) | какие элементы в строке пайплайна |
| 6 | `installVideoSegmentClipProbe` (`video_probe_gst.go`) | на каком паде обрезать |
| 7 | `reusePipeline` (`pipeline_gst.go`) | какие элементы гонять READY→PAUSED при перемотке |

Плюс `ProbeInfo.DemuxerName()` и построение `CODECS` в `handlers.go`.

Это не семь решений. Это одно решение и семь его независимых проекций. Проекции расходятся —
и **оба уже случившихся дефекта были расхождением**, а не ошибкой в логике:

- точность (#4) сказала «да» там, где обрезка (#6) не стояла → перемотка уезжала назад;
- обрезка встала на видео (#6), но не на звук → звук опережал картинку на длину GOP.

Оба чинились правкой одной проекции. Оба воспроизводимы снова, потому что причина —
не значения, а форма: **согласованность держится на дисциплине, а не на типах.**

### 1.1. Живой дефект: неизвестный кодек принимается и даёт пайплайн без видео

`codecToCapsName` для видео возвращает ровно шесть значений: пять известных caps или `""`.
Прогон по реальным кодекам:

```
MPEG-4 Video            caps=""   transcoded=false   validate=<nil>
Xvid                    caps=""   transcoded=false   validate=<nil>
MPEG-2 Video            caps=""   transcoded=false   validate=<nil>
VC-1                    caps=""   transcoded=false   validate=<nil>
Windows Media Video 9   caps=""   transcoded=false   validate=<nil>
Motion JPEG             caps=""   transcoded=false   validate=<nil>
H.263                   caps=""   transcoded=false   validate=<nil>
Theora                  caps=""   transcoded=false   validate=<nil>
```

`validate=<nil>` — файл принят. `transcoded=false` — идём в passthrough. А в passthrough
`createPipelineArgs` разбирает случаи `IsH264/IsH265/IsAV1/IsVP9` **без `default`**, и не пишет
ничего. Что получается для Xvid в MKV:

```
souphttpsrc ... ! matroskademux name=d multiqueue name=mq ... d.video_0 ! mq.sink_0
mp4mux name=mux fragment-mode=dash-or-mss fragment-duration=6000 streamable=true ! appsink name=out
```

`mq.src_0` не связан ни с чем, у `mp4mux` нет ни одного входа. Пайплайн не может сделать preroll.

Задеты не экзотические случаи: **ASF/WMV — это всегда VC-1 или WMV3**, то есть asfdemux
поддержан целиком впустую; FLV с H.263/VP6 — так же; MKV со старым DivX/Xvid — обычная
раздача. Матрица форматов в [seek-accuracy](gstreamer-seek-accuracy.md#матрица-форматов)
утверждает, что ASF и FLV идут через транскод, — это неверно, исправлено вместе с этим
документом.

Корень: ветка `default: return probe.VideoCapsName() != ""` в `videoIsTranscoded` выглядит как
«неизвестное — перекодируем», но `""` — и есть представление неизвестного, поэтому ветка
**всегда возвращает `false`**. Условие никогда не истинно.

### 1.2. Тест, который это прикрывает

```go
func TestUnknownVideoCodecUsesTranscodePipeline(t *testing.T) {
    runner.task.Probe.Tracks[0].CapsName = "video/x-theora"   // парсер такого не выдаёт
    ...want "mq.src_0 ! decodebin !"
}
```

Тест ставит `CapsName` руками в значение, которое `codecToCapsName` **не может вернуть**
(для Theora она возвращает `""`). Он проверяет ветку, недостижимую на реальном входе, и
зелёный цвет означает ровно ничего. Это не небрежность в тесте — это следствие того, что
«неизвестный кодек» не является значением домена: его приходится подделывать.

### 1.3. Мёртвый флаг

`TranscodeVP8` объявлен, сохраняется в настройки, читается из них — и **не используется нигде**.
VP8 попадает в тот же `default` и перекодируется всегда:

```
VP8 TranscodeVP8=false -> transcoded=true
VP8 TranscodeVP8=true  -> transcoded=true
```

Поведение случайно правильное (VP8 в fMP4 не бывает), настройка — ложь.

### 1.4. Согласованность, которая держится на инварианте из другого файла

`installVideoSegmentClipProbe` в режиме passthrough ставит барьер только для H.264/H.265 —
у остальных нет элемента `video_timestamper`. При этом AV1/VP9 в MKV получают Cue, а значит
`seekCanBeAccurate() == true`: просим точность, обрезки на видео нет, на звуке — есть.

Сегодня это не стреляет, потому что при наличии Cue `seekToSegmentLocked` всегда перематывает
ровно на точку индекса, то есть на keyframe, и обрезать нечего. Но этот инвариант живёт в
`task.go`, а зависит от него код в `video_probe_gst.go`. Ничто его не удерживает: любая
перемотка не по индексу немедленно даёт рассинхрон звука и картинки на AV1/VP9.

## 2. Целевая модель: три слоя

Ключ не в том, чтобы завести «таблицу возможностей форматов». Если все семь мест продолжат
**сами** её опрашивать своими `switch`, ничего не изменится — расхождение просто переедет.

Менять надо не источник фактов, а момент вычисления: решение принимается **один раз**,
становится значением, дальше только читается.

### Слой 1 — Возможности источника (факты, без политики)

Что представляет собой файл. Выводится **только из `ProbeInfo`**, `Config` здесь недоступен.

```go
type ContainerKind int   // Matroska | ISOBMFF | AVI | ASF | FLV | ContainerUnknown
type VideoCodec int      // H264 | H265 | AV1 | VP9 | VP8 | VideoCodecUnknown
type IndexKind int       // MatroskaCues | MP4SyncSamples | NoIndex

type VideoCapability struct {
    Codec       VideoCodec
    Parser      string   // "h264parse"; "" — копирование невозможно
    Timestamper string   // "h264timestamper"; "" — нет
    MuxCaps     string   // caps перед mux.video_0
    HDR         bool
    Width, Height, FrameRateNum, FrameRateDen int
}

type SourceCapabilities struct {
    Container ContainerKind
    Demuxer   string
    Index     IndexKind
    Video     VideoCapability
    Audio     []AudioCapability
    Subtitles []SubtitleCapability
}
```

Две таблицы — контейнеров и кодеков — и ничего больше. Существенно, что
`VideoCodecUnknown` — **полноправное значение** с пустым `Parser`. Пустой `Parser`
механически означает «скопировать нельзя», и §1.1 перестаёт быть представимым: не бывает
«копируем неизвестный кодек», потому что копировать нечем.

### Слой 2 — Политика (`Capabilities × Config × ClientProfile → Plan`)

Одна функция `resolvePlan`. **Все** проверки `Transcode*` живут здесь и только здесь.

```go
type VideoMode int   // VideoCopy | VideoTranscode | VideoToneMapTranscode
type AudioMode int   // AudioCopy | AudioEncode
type SegmentKind int // SegmentsFromIndex | SegmentsFixed

type Plan struct {
    Demuxer  string
    Video    VideoPlan     // Mode + элементы + имя пада для обрезки
    Audio    AudioPlan
    Segments SegmentPlan   // Kind, SegmentSeconds, FragmentDurationMS
    Seek     SeekPlan      // Accurate, ClipPads, ResetElements
    Subtitles []SubtitlePlan
}

func ResolvePlan(caps SourceCapabilities, conf Config, client ClientProfile) (Plan, error)
```

Три расходившихся факта становятся **полями одной структуры, вычисленными рядом**:

- `Seek.Accurate`;
- `Seek.ClipPads` — выводится из `Video.Mode` в тех же пяти строках, что и `Accurate`;
- `Segments.Kind`.

`videoSeekFlags` становится методом `SeekPlan`. Взаимоисключение флагов
([seek-accuracy §флаги](gstreamer-seek-accuracy.md#флаги-перемотки-несовместимы-между-собой))
перестаёт быть договорённостью: наружу торчит один `bool`, наборы выводятся из него.

Отказ — тоже результат политики, а не отдельная функция `validateProbe`. Правило «AVI требует
`TranscodeAVI`» перестаёт быть особым случаем: это просто строка, где `Copy` недоступен, а
`Transcode` запрещён конфигом → `error` с внятным текстом **до** создания задачи.

### Слой 3 — Реализация (`Plan → строка пайплайна, пробы, перемотка`)

`createPipelineArgs` становится сериализатором `Plan` **без единой ветки политики**.
`installVideoSeekProbes` читает `plan.Seek.ClipPads` вместо повторного `videoIsTranscoded`.
`reusePipeline` читает `plan.Seek.ResetElements` вместо своего `videoIsTranscoded`.

`Plan` вычисляется один раз в `NewTask` и лежит на `Task`. `Task.Config` и `Task.Probe`
остаются для логов и диагностики, но **поведение из них больше не выводится**.

## 3. Что становится непредставимым

Ценность модели измеряется не тем, что она позволяет, а тем, что запрещает:

| Сегодня возможно | После |
|---|---|
| точная перемотка без обрезки | `Accurate` и `ClipPads` — соседние поля одного конструктора |
| обрезка видео без обрезки звука | `ClipPads` — один список, заполняется целиком |
| принять файл и построить пайплайн без видеоветки | `Parser == ""` ⇒ `Copy` недоступен ⇒ либо транскод, либо явный отказ |
| настройка, которую никто не читает | флаг, не участвующий в `ResolvePlan`, виден в golden-таблице как строка, не меняющая план |
| «поддержан демиксер» ≠ «поддержан формат» | одна строка таблицы отвечает за пару целиком |

## 4. Конфигурация: шесть `Transcode*` — неверная модель

`TranscodeH264/H265/AV1/VP9/VP8/AVI` описывают **не сервер, а клиента**: «что не умеет
проиграть тот, кто смотрит». Отсюда и глобальность: один телевизор с H.265 заставляет
перекодировать для всех, а браузер без H.265 — наоборот.

[Бэклог capability-aware playback](torrent-mod-playback-capability-fallback-backlog.md) уже
предлагает передавать профиль (`direct` / `transcode`) в URL задачи. Целевая сигнатура это
учитывает: `ResolvePlan(caps, conf, client)`, где `client` — что клиент подтвердил через
`canPlayType`/`isTypeSupported`, а `conf` остаётся серверным потолком (лимиты железа, битрейт,
HDR→SDR). Флаги `Transcode*` при этом становятся дефолтом профиля, а не глобальным
переключателем — и это **не требует** менять их прямо сейчас: `ClientProfile` вводится
параметром с нейтральным значением и наполняется, когда бэклог дойдёт до реализации.

Отдельно: `UseGPU` сегодня значит две разные вещи — выбор аппаратного энкодера
(вместе с `HardwareAcceleration`) и `use-opencl` у `hdrtonemap`. Разделить при переходе.

## 5. Тесты: одна golden-таблица вместо четырёх наборов

Сегодня четырём предикатам нужны четыре теста, каждый из которых может быть зелёным, пока
**комбинация** неверна — ровно это и произошло дважды. `Plan` даёт единую точку:

```
(контейнер, видеокодек, аудиокодек, конфиг, профиль) → полный Plan
```

Строк порядка `6 × 6 × 2` с отсевом невозможных — обозримо и печатается целиком. Свойства,
проверяемые поверх таблицы, а не построчно:

- `Seek.Accurate ⇒ len(Seek.ClipPads) > 0` и в списке есть и видео, и звук;
- `Video.Mode == VideoCopy ⇒ Video.Parser != ""`;
- каждый элемент, упомянутый в `Seek.ClipPads` и `Seek.ResetElements`, присутствует в строке
  пайплайна, построенной из того же плана;
- любой принятый план даёт строку пайплайна, где связаны все `mq.src_*`.

Последнее свойство ловит §1.1 напрямую и стоит одного прохода строкой.

Живой прогон эти тесты не заменяют: они фиксируют решения, а не поведение GStreamer.

## 6. Миграция: каждый шаг отгружаем

1. Ввести `SourceCapabilities` и `ResolvePlan`, **никем не используемые**. Golden-таблица
   фиксирует **текущее** поведение, включая заведомо неверные строки — помеченные как таковые.
2. Переписать четыре предиката делегатами к полям `Plan`. Существующие тесты — сеть
   безопасности: они обязаны остаться зелёными без правок.
3. `createPipelineArgs` читает `Plan`.
4. Пробы и `reusePipeline` читают `Plan`.
5. Удалить предикаты и `validateProbe`.
6. **Только теперь** чинить неверные строки таблицы: неизвестный кодек, `TranscodeVP8`,
   пропущенная обрезка на AV1/VP9.

Шаги 1–5 не меняют поведения — их можно проверять существующими тестами. Шаг 6 меняет, и
каждая правка видна как diff одной строки в golden-таблице.

Порядок важен: чинить §1.1 до шага 5 значит вносить исправление в код, который всё равно
будет удалён, и без таблицы, показывающей побочные эффекты.

## 7. Что осознанно не делаем

- **Универсальный движок согласования возможностей.** Вселенная — шесть контейнеров на шесть
  кодеков. Таблица нужного размера; движок — нет.
- **Иерархию интерфейсов вместо `Plan`.** Обычные структуры, посчитанные один раз. Полиморфизм
  здесь только спрячет ту же развилку обратно в семь мест.
- **Втягивать `CODECS` из `handlers.go`.** Он строится из init-MP4, то есть из **факта на
  выходе**, а не из намерения. Смешивать источники истины не нужно; сверить их — можно тестом.
- **Трогать `mp4box.go`.** Ремукс — отдельный слой ниже плана, план в него не заглядывает.

## 8. Открытые вопросы

- **MP4/MOV `stss`.** В модели это один новый `IndexKind` и одна строка политики. Стоит ли
  реализация — вопрос статистики раздач, а не архитектуры: MKV и AVI уже точные.
- **Неизвестный кодек: транскод или отказ?** Транскод через `decodebin` вытянет Xvid и MPEG-2,
  но не гарантирован для экзотики. Предлагается транскод плюс явная ошибка, если `decodebin`
  не собрал ветку, — но проверять на живых раздачах.
- **Где живёт `ClientProfile`.** Приходит из URL по бэклогу; ключ задачи от него зависит,
  иначе два клиента с разными профилями поделят один пайплайн.
