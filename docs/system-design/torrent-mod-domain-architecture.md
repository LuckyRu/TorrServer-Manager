# Доменный слой Torrent Mod: Store, State, Interactors

Процессный документ: архитектура домена экрана результатов Torrent Mod (`Plugins/TorrentModPlugin/domain/`
и `shared/core/`) в её финальном, текущем виде — плюс почему она такая, какие альтернативы были отвергнуты
и какой класс багов эта архитектура закрывает структурно, а не точечными патчами. Это не хронология всех
промежуточных версий — предыдущие дизайны (View/ViewModel с callback'ами, callback-based retry на
`ensureSeasonLoaded`) упомянуты только там, где нужно объяснить, от чего именно ушли и почему.

## Актуальный поисковый контекст

Экран результатов не содержит обычного поля поиска и не принимает ручную замену названия. Произведение
приходит из TMDB, после чего домен строит запросы по его имени, сезону и эпизоду; если TMDB не дала
подходящий контекст, пользователь не переводится в альтернативный ручной поиск. `Lampa.Filter` используется
только для сезона, типа перевода, студии и качества.

## Принцип: UI-логика — во View, даже когда она управляется доменными данными

Общее правило, к которому эта архитектура возвращалась несколько раз с исправлениями: анимации, таймеры
затухания, любая чисто визуальная логика — это ответственность View-слоя, а не домена, **даже если** она
триггерится изменением доменных данных. Домен обязан хранить факты (например, «этот трекер ответил
успешно и когда именно»), но не должен знать, что с этими фактами нужно подождать 4 секунды и красиво
скрыть. Реальный инцидент, где таймер затухания сначала попал в домен, был исправлен по прямому указанию
автора проекта, и на этом инциденте сформулирован сам принцип — подробности в
[`torrent-mod-parallel-search.md`](torrent-mod-parallel-search.md), здесь не повторяются.

## Персистентность выбора фильтров — текущее поведение

Выбор сезона/типа перевода/студии/качества переживает переоткрытие экрана, по образцу другого Lampa-плагина
(Online Mod, `Lampa.Storage.get`/`Lampa.Storage.cache`). Двухуровневая схема: глобальный дефолт
(`torrent_mod_voice`/`torrent_mod_translator`/`torrent_mod_quality`/`torrent_mod_bitrate`) плюс покрытие на уровне конкретного фильма/сериала
(`torrent_mod_last_season`/`torrent_mod_last_voice`/`torrent_mod_last_translator`/`torrent_mod_last_quality`,
`Lampa.Storage.cache(name, 200, {})`, ключ — `movie.id`), которое всегда побеждает глобальный дефолт, если
присутствует. `Storage.cache()` только читает и подрезает список по лимиту — не персистит сама, поэтому
каждое изменение всё равно требует явного `Storage.set()`. У сезона нет смыслового глобального уровня
(номера сезонов не переносятся между произведениями), только память по конкретному фильму/сериалу, поверх
уже существующей эвристики «на чём я остановился» (`initialSeason()`, основана на данных Timeline из
Lampa) как фолбэка, а не замены — это два разных сигнала («какой сезон я просматривал» и «до какой серии я
досмотрел»), оба стоит хранить отдельно. «Сбросить фильтр» тоже персистит `'any'`, а не только меняет
состояние в памяти — иначе сброс не «прилипал» бы к следующему визиту.

## От View/ViewModel к Store/State/Interactors

Более ранний дизайн экрана результатов (View, читавший данные через явные callback-методы ViewModel) был
заменён по прямому запросу — «доменная логика должна жить в домене» — на настоящий доменный слой: State +
Interactors, где View подписывается на изменения состояния вместо того, чтобы его дёргали именованными
методами. `Plugins/TorrentModPlugin/domain/` состоит из:

- **`store.js`** — generic pub-sub на ~25 строк: `get()`/`subscribe(listener)`/`patch(partial)`. `patch`
  мелко (shallow) мёржит в **новый** верхнеуровневый объект, так что нетронутые поля сохраняют старую
  ссылку — это делает `state.x !== previous.x` валидной дешёвой проверкой изменений без глубокого diff'а.
  У стора нет знания о домене — ни «сезона», ни «устаревания», ничего специфичного.
- **`results-core.js`** — содержимое не менялось, файл просто переехал из `ui/` в `domain/`, потому что и
  так уже был чистой доменной логикой, только лежал не там.
- **`results-state.js`** (`createInitialResultsState`) — только плоские данные. Специально нет ничего
  похожего на живой Promise в состоянии (был `seasonPoolPromise`, убран) — вместо него enum-статусы и
  generation-счётчики: простые, сравнимые, отображаемые значения.
- **`results-selectors.js`** — вычисляемые данные (`selectBusy`, `selectFilterChipData`,
  `selectEpisodeBadges` и т.д.), пересчитываются заново при каждом вызове, никогда не хранятся — по той же
  причине, по которой отдельно поддерживаемый флаг может разъехаться с реальностью: чистая функция над уже
  сохранёнными полями не может разъехаться с ними структурно.
- **Три интерактора**, сгруппированные по реальным связям вызовов/данных, а не по поверхностной похожести
  темы: `episodes-interactor.js` (`loadEpisodes`/`ensureSeasonPool`/`setSeason`/`showEpisodeList` — эти
  функции уже вызывали друг друга напрямую и делят один и тот же набор season-scoped ресурсов),
  `selection-interactor.js` (`selectEpisode`/`playCandidate` — все сходятся в одном `finishSelection`),
  и `filters-interactor.js` (`setVoiceFilter`/`setTranslatorFilter`/`setResolutionFilter`/`resetFilters`) —
  сознательно отдельно от асинхронной пары выше: синхронный, без сети, без забот об устаревании — это
  действительно другая *форма* процесса, объединение с асинхронными размыло бы обе.
- **`results-domain.js`** — композиционный корень (`createResultsDomain`), с одним общим флагом
  уничтожения на оба асинхронных интерактора, а не по одному на каждый.

### Независимые статусы вместо одного enum

`episodesStatus` и `poolStatus` (каждый `'idle'|'loading'|'ready'|'error'`) держатся раздельно, потому
что управляют независимыми кусками UI: содержимым списка серий и пулом раздач. Глобальное «занято ли
что-нибудь» (`selectBusy`) — чистая производная над ними, а не третье отдельно поддерживаемое поле.

### Generation-счётчики вместо сравнения значений

Устаревание/зависимости ответов раньше проверялись тремя независимыми, слегка несогласованными ad hoc
сравнениями (`state.season !== requestedSeason`, `state.seasonPoolSeason !== state.season`, и т.п.,
добавлявшимися по одному во время более ранней закалки кода). Заменены монотонным счётчиком
(`seasonGeneration`/`poolGeneration`), который увеличивается тем интерактором, что запускает новую
асинхронную операцию, захватывается этим вызовом и сравнивается с **текущим значением стора** в момент,
когда ответ приходит. Это закрывает реальный пробел, который сравнение значений в принципе не может
закрыть: переключить сезон 2 → 3 → 2 снова быстро — и *первый* поздний ответ по сезону 2 пройдёт наивную
проверку `season !== requestedSeason` (сезон действительно снова 2), хотя параллельно уже летит второй,
более новый запрос по тому же сезону 2, и именно он должен победить. Узкий кейс (нужны два переключения на
одно и то же значение в пределах одного сетевого round trip), но реальный класс бага, который простое
сравнение значений структурно не исключает. Сознательно **не** зашито в сам `store.js` (например, общий
`patchIfCurrent(key, expected, partial)`) — политика устаревания специфична для домена (какой счётчик
охраняет какое поле), а протаскивание её в generic pub-sub смешало бы переиспользуемый примитив с
политикой, у которой всего два места применения; дедупликация осталась в доменном слое, который её
действительно понимает.

### Цикл рендера View — подписки на проекции state

`store.subscribeSelector(select, listener, equal)` хранит предыдущий результат селектора и вызывает
listener только при изменении этой проекции. `Lifecycle.subscribeSelector()` регистрирует отписку в
scope экрана. View подписывается раздельно на content, бейджи эпизодов, фильтр, статус, трекеры и пикер,
а не сравнивает вручную длинный список полей в одном `render(state, previous)`.

Например, бейджи зависят от `pool`, `episodesCache`, статусов поиска, сезона и единого
`state.filters`; поэтому смена любого фильтра автоматически пересчитывает
`selectEpisodeBadges()`. Список студий — не отдельное поле state, а производный
`poolTranslators(state.pool)`. В state остаются только первичные факты и пользовательское намерение:
`state.filters = {voiceType, translator, resolution, bitrate}`. Это исключает рассинхронизацию
«фильтр уже применён, а данные строки ещё старые».

### Playback сознательно остаётся вне Store/Domain

`playback/smart-preload.js` вызывается как обычная межмодульная функция (`startDownload(item, target)`) из
`selection-interactor.js`, а не как часть доменного стора. Сессия воспроизведения намеренно развязана с
экраном результатов: после прямого `Lampa.Player.play()` плеер может пережить Activity результатов, пока
сессия сама владеет опросом метаданных и слушателями следующей серии до тех пор, пока плеер не будет
уничтожен или новая закачка не вытеснит старую. У неё нет ни оверлея, ни состояния в сторе результатов, так
что встраивание в домен добавило бы состояние, которое View результатов никогда не читает, и усложнило бы
независимый жизненный цикл playback-сессии.

## `shared/core/`: общие примитивы надёжности

Введены после того, как автор проекта отклонил очередной раунд точечных фиксов как «местячковое
мероприятие» и запросил настоящую архитектуру: обработку ошибок/retry/fallback как domain-level концепцию,
а не разбросанные по файлам `if`. Этому предшествовала полная живая инвентаризация всех уже существующих в
плагине паттернов ошибок/retry/fallback (прочитаны все, не угаданы), затем — оценка целевой формы до
написания кода. Найдено:

- четыре почти идентичных вручную написанных места проверки устаревания (bump generation-счётчика → patch
  «загрузка» → await → guard `isDestroyed()||generation mismatch` → commit) в
  `domain/episodes-interactor.js`/`domain/selection-interactor.js`;
- два независимо изобретённых механизма «жив ли ещё этот экран», делающих одну и ту же работу
  (`results-domain.js`'s `isDestroyed()` против `playback/smart-preload.js`'s `session.alive`);
- нигде не было структурированного типа ошибки — `notify()` (`shared/utils.js`) принимает голую строку, а
  возможность повтора решалась ad hoc для каждого места вызова, **уже непоследовательно**: `startMovie()`
  и `showMoviePool()` показывали идентичное сообщение «раздачи ещё загружаются» для идентичного
  предусловия, но только один из них планировал повтор;
- по ходу миграции обнаружился мёртвый код: `metadata/tmdb.js`'s `fetchSeason` содержал `.catch(() => [])`,
  который никогда не срабатывал — `shared/utils.js`'s `request()` построен на Promise, который никогда не
  реджектится (сетевая ошибка резолвится в `null`, той же формой, что и «данных нет»), так что сетевая
  ошибка TMDB и легитимно пустой сезон были структурно неразличимы.

### `shared/core/result.js`

`ok(value)`/`err(kind, message, {retryable, cause})` — Result-форма, применённая только там, где она
реально закрывает пробел (`fetchSeason` выше). Сознательно **не** применена к
`search/search-backend.js`'s `{results, indexers, failed}`, которая уже информационно эквивалентна
двухисходному Result для своих трёх текущих вызывающих — конвертация была бы churn'ом без исправленного
бага.

### `shared/core/generation-guard.js`

Одна функция, `isCurrentGeneration(store, generationKey, generation, isDestroyed, isStillValid)`, заменяет
собой проверки устаревания в `loadEpisodes`, `loadAllTorrents` и `ensureSeasonLoaded`. Дополнительный
`isStillValid` оставлен для узких случаев, где одного совпадения generation недостаточно. Ручного поиска
по альтернативному названию в домене нет, поэтому отдельный search-generation для него не нужен. Сознательно
**не** сделана более крупная обёртка «guarded task»,
объединяющая ещё и bump/patch/commit — то, что каждое место реально коммитит в стор при успехе, различается
слишком сильно (плоское поле статуса против записи в карту `seasonLoads[season]` против отдельной,
не связанной с generation'ами дедупликации in-flight запросов у `loadAllTorrents`), чтобы протащить всё
через одну форму `onStart`/`onResult` без лишней косвенности над кодом, который и так нормально читался.

### `message.retry`: от boolean к функции

`message.retry` расширен с `boolean` до `Function|null` (`domain/results-state.js`). Единственное место в
кодовой базе, которое уже правильно делало retryable-error UX (`stage:'message'` + реальная строка
«Повторить» в `showMessage()`, `ui/results-screen.js`), захардкодило, **какую именно** функцию означает
`true` (`domain.episodes.loadEpisodes`, безусловно), вместо того чтобы нести саму функцию для вызова —
из-за чего мог существовать только один производитель такого сообщения. Расширение (обычная ссылка на
функцию ничем не отличается по типу от callback'ов `onLoaded`/`onComplete`, которые и так текут через эту
кодовую базу повсюду — правило состояния «только плоские данные» было про запрет хранить живой Promise, а
не про запрет функций) позволило `freshSearch`'у на неудаче Jackett стать вторым производителем, заменив
голый `notify()`-тост, который просто гас, той же самой кнопкой повтора, что уже была у TMDB-неудачи в
`loadEpisodes` — две неудачи, которые для пользователя означают одно и то же («не удалось загрузить,
попробуй ещё раз»), теперь получают одинаковый UX.

### `shared/core/lifecycle.js`

`createLifecycle()` → `{isAlive, dispose}`, унифицирует **форму** двух независимо изобретённых флагов
живости (`isDestroyed()`/`session.alive`), но не их времена жизни — playback намеренно продолжает жить
дольше экрана результатов, и это остаётся верным. В этом проходе на него мигрировал флаг `destroyed` из
`results-domain.js`; половина `playback/smart-preload.js` намеренно **не** тронута.

### Что оставлено как есть, и почему

`playback/smart-preload.js` (`session.alive`, ограниченный retry в `pollFiles`, необёрнутая 3-уровневая
цепочка fallback'ов в `registerTorrent`) оставлен без изменений в этом проходе — не забыт: на нём нет
открытого бага (это архитектурная симметрия, а не фикс), у него **ноль** автотестового покрытия
(подтверждено grep'ом) и он документирован как территория «только живая проверка», а реальная
мотивирующая проблема — несогласованный retry/error UX — целиком жила в `domain/`, который тестами
покрыт. Когда до playback дойдёт очередь, это стоит сделать одним проходом (`shared/core/poll.js` + доля
`lifecycle.js` для playback + рефакторинг `registerTorrent` в плоские шаги на Promise, всё вместе, не тремя
отдельными изменениями), с полным ручным прогоном воспроизведения в конце.

### `shared/core/log.js`

Небольшое дополнение той же волны: единый хелпер `log(scope, message, data)`/`warn(scope, message, data)`
(формат `Torrent Mod [scope]: message`), запрошенный отдельно — подробное консольное логирование
жизненного цикла по всему плагину. Заменил разрозненные `console.log('Torrent Mod: ...')`/`console.warn`
без единого префикса и scope на один хелпер, вызываемый из каждого слоя, где есть за чем следить в
консоли: `index.js`, `ui/torrent-mod-component.js`, `domain/results-domain.js`,
`domain/episodes-interactor.js`, `domain/selection-interactor.js`, `playback/smart-preload.js`. Сознательно
не тронуты `notify()` (это UI-уведомление, а не лог жизненного цикла) и отдельная,
`torrent_mod_debug`-гейтованная таблица оценённых кандидатов (диагностика по запросу, другая аудитория).
Для анализа качества входных данных поиск дополнительно пишет по одной записи
`metadata-parse: раздача` на каждый сырой результат Jackett: исходный заголовок, технические поля,
распознанный release и возможную ошибку парсинга. Этот лог выполняется до title-gate, поэтому его можно
сопоставить с последующей диагностикой фильтрации.

## Уроки закалки кода (hardening passes)

Два независимых прохода ревью (архитектор по границам модулей/import-графу, программист по гонкам
времени выполнения) читали реальный текущий исходник, не саммари. Из находок этих проходов ниже — только
то, что относится к доменному слою; находки по `playback/`/`search/` (переупорядочивание таймаута
воспроизведения, guard от двойного клика на закачку, null-guard в маппинге ответов поиска, мутация
кандидата при скоринге) относятся к другим слоям и здесь не описаны.

Первый проход нашёл: отсутствие guard'а устаревания в двух асинхронных функциях (`loadEpisodes()` и
`selectEpisode()`'s fresh-search branch) — именно этот класс бага и есть причина, по которой существует
примитив `generation-guard.js`, описанный выше; и отсутствие проверки «жив ли ещё экран» — тот же класс
бага, закрытый впоследствии примитивом `lifecycle.js`.

Этот же проход зафиксировал явный список того, что **сознательно не сделано, и почему**: полноценная
система типов (TypeScript или `// @ts-check` + `tsc`), закоммиченный/CI-gated тестовый набор,
runtime-библиотека схемной валидации (в духе zod/ajv) на границах модулей, и блокетный `Object.freeze()` на
данных, пересекающих границу модуля. Все они потребовали бы либо новой build-зависимости, которой у
проекта раньше не было, либо вошли бы в конфликт с рабочим паттерном мутации при скоринге без более
крупного рефакторинга. Чистые функции скоринга/парсинга уже вручную верифицируются одноразовым Node-
харнессом именно тогда, когда меняется гейтующая математика — это признано достаточным уровнем инвестиций
для кодовой базы такого размера, с одним постоянным автором и без заявленных амбиций стать
универсальным фреймворком. Эта оценка остаётся в силе и сегодня.

Второй проход, позже, нашёл в доменном слое следующие дефекты старого ручного поискового пути; после
отказа от этого пути они удалены вместе с поддерживавшим их состоянием:

- **Старый `customQuery` не был единым контекстом для целей и скоринга** — это создавало расхождение
  между бейджами, пикером и запуском. Состояние ручного запроса удалено; все цели и проверки теперь
  используют один TMDB-контекст.
- **Один и тот же поиск для фильма с уточнённым названием мог делать два идентичных round trip'а к Jackett**.
  Уточнение названия удалено из UI и домена, поэтому этот класс повторных запросов больше невозможен.
- **Магическая строка-ключ кэша дублировалась в двух файлах** (`'torrent_mod_last_season'` — именованная
  константа в `episodes-interactor.js` на стороне записи, но отдельный строковой литерал в
  `filters-interactor.js` на стороне чтения) — ничего не гарантировало их согласованность; переименование
  одного молча сломало бы память сезона по фильму без единой ошибки где-либо. Перенесена в `shared/state.js`
  как `SEASON_CACHE_KEY`, импортируется обеими сторонами.
- **Строки-режимы `'movie'`/`'series'` были нетипизированными литералами**, задублированными примерно в 10
  местах вызова по `search/`, `playback/`, `domain/`, без единого источника истины — опечатка молча
  попадает в ветку `else`, а не выдаёт ошибку (в проекте сознательно нет TypeScript/линтера). Добавлены
  `MODE_MOVIE`/`MODE_SERIES` в `shared/state.js`, заменены все литералы.

Этот же проход отдельно подтвердил (не «наверное», а проверив архитектором): нет циклических зависимостей,
а разделение фильм/сериал на уровне домена и View — не дублирование логики: обёртки
`domain/movie-results-viewmodel.js`/`series-results-viewmodel.js` — тонкие 22-строчные проброски к одному
`createResultsDomain`, `ui/movie-results-view.js`/`series-results-view.js` — 9-строчные проброски к одному
`createResultsView`; `hasSeasons` — обычный параметр ветвления, не второй механизм.

## Селекторы для пикера и бейджей: показывать то, что реально произойдёт

Два связанных UX-фикса, тоже доменного (селекторного) слоя:

- **Начальная позиция курсора в пикере** (`ui/results-screen.js`'s `openPickerPanel`) — раньше пикер всегда
  открывался с фокусом на первом элементе. Теперь `selectedNode` захватывается при построении строк (тот
  же флаг `selected`, который уже управлял маркером «Выбрано») и передаётся в `toggle()` пикера, заменяя
  слепой `collectionFocus(false, ...)` на `collectionFocus(selectedNode || false, ...)`.
- **Бейдж серии показывает то, что реально будет запущено по клику**, а не просто кандидата с наивысшим
  рангом (`domain/results-core.js`'s `badgeText`, `domain/results-selectors.js`'s `selectEpisodeBadges`) —
  оба получили опциональный параметр `saved`/`seasonDefault`, который предпочитается `matches[0]` через уже
  существующую `findSavedDefault` (ту же функцию, которую уже использует решение об автоплее в
  `selectEpisode`), так что бейдж и реальный выбор воспроизведения больше не могут визуально расходиться.

Важное архитектурное свойство: доменный слой остаётся Lampa-агностичным намеренно — вместо того чтобы
чистые селекторы напрямую трогали `Lampa.Storage`, `selection-interactor.js` предоставляет тонкий
read-only аксессор (`getSeasonDefault(season)`, обёртка над уже приватной `readSeasonDefault`), а View сам
передаёт значение внутрь.

## Класс бага: рекурсивный синхронный callback (`RangeError`)

Два падения `RangeError: Maximum call stack size exceeded` в разное время имели одну и ту же
архитектурную причину: ленивая функция загрузки (`ensureSeasonLoaded`), когда реальной работы сделать ещё
не могла, всё равно синхронно вызывала свой собственный callback «позови меня, когда что-то изменится» —
хотя ничего не изменилось, — а вызывающая сторона со своей retry-логикой тут же звала её снова, уходя в
бесконечную синхронную рекурсию. Первое падение было исправлено узко (не звать callback только для одного
конкретного «ещё не устоявшегося» состояния). Второе падение оказалось той же формой в другой ветке той же
функции несколько дней спустя, плюс ещё две теоретически достижимые, но пока не сообщённые ветки с тем же
изъяном, найденные при расследовании. Второй фикс (очередь отложенных callback'ов,
`pendingSeasonCallbacks`) был рабочим, но всё ещё узко заточен под конкретные ветки — и сам был заменён
финальным структурным решением ниже.

### Финальное решение: убрать контракт callback'а совсем

Это был уже третий независимый триггер идентичного бага, и предложенный «ещё один общий фикс» всё равно
потребовал бы четвёртой предварительной проверки, чтобы закрыться полностью. Вместо очередного патча —
редизайн:

- **`ensureSeasonLoaded(season)` (`domain/episodes-interactor.js`) лишилась параметра `onComplete`
  целиком** — никакого callback'а, никакой очереди `pendingSeasonCallbacks`. Теперь это чисто
  fire-and-forget и идемпотентная функция: проверить `seasonLoads[season]`, запустить запрос, если ничего
  не выполняется, записать `pool`/`seasonLoads` в стор, когда он разрешится. Она понятия не имеет о
  пикерах, кликах или какой-либо retry-логике вызывающей стороны — удаление callback'а **целиком**, а не
  просто более безопасный вызов, и есть то, что реально устраняет весь класс бага: больше не существует
  формы «повтор через callback», в которой вызывающая сторона могла бы ошибиться, структурно, независимо
  от того, сколько веток раннего выхода эта функция обрастёт в будущем.
- **Содержимое бокового пикера перестало отдельно храниться в сторе.** `state.picker`
  (`results-state.js`) теперь содержит только `{open, episode}` — поля `items`/`status`/`target`/
  `selectedId`, которые раньше императивно заполнялись удалённой `fillPicker`, теперь вычисляются
  `selectPickerData(object, state, seasonDefault)` — новым чистым селектором, выводящим их заново из
  `state.pool`/`state.seasonLoads`/`state.poolStatus` при каждом вызове — ровно тем же
  паттерном, что уже использовал `selectEpisodeBadges` для бейджей строк, просто ранее не распространённым
  на пикер. `openPicker`/`closePicker`/`playPickerCandidate` (`domain/selection-interactor.js`) сжались до
  одиночных вызовов `store.patch({picker:{...}})` вообще без бизнес-логики внутри.
- **Один реактивный наблюдатель (`store.subscribe`, `selection-interactor.js`) заменяет собой каждое
  место, где раньше протаскивался callback завершения.** `ensureSeasonLoaded` только пишет состояние; этот
  наблюдатель — единственное место, реагирующее на эту запись, чтобы решить, что (если вообще что-то)
  должно произойти дальше: запускает ленивую загрузку сезона, когда пикер открыт и пуст для него (безопасно
  вызывать при каждом изменении состояния — `ensureSeasonLoaded` идемпотентна), и повторяет клик, случившийся
  пока данные ещё грузились (`pendingClick`). Наблюдатель, вызывающий `store.patch()`, синхронно
  перезапускает сам себя один раз (`patch()` в `store.js` вызывает слушателей синхронно) — это ограничено,
  а не бесконечно, поскольку второй проход всегда застаёт сезон уже `'loading'`/устоявшимся и ничего
  больше не делает — та же форма, что у любого корректного `useEffect`-подобного реагирования, а не новый
  экземпляр исправляемого бага.
- **Итог по объёму кода**: `ensureSeasonLoaded` в `episodes-interactor.js` сократилась примерно с 75 строк
  (со своей картой очередей и трёхветочным блоком раннего выхода) до примерно 25; `fillPicker` и
  `buildPickerTarget` (`selection-interactor.js`) удалены целиком, заменены ~20-строчным селектором плюс
  одним общим наблюдателем. Собранный бандл стал меньше после рефакторинга, а не больше, несмотря на новые
  наблюдатель/селектор.

**Общий урок**: устранение контракта, формой своей провоцирующего ошибку, побеждает попытку сделать
аккуратным каждого текущего вызывающего этого контракта.

## Виджет прогресса поиска: дизайн-решения

Динамический виджет прогресса поиска (спиннер, эскалирующий текст статуса для медленных холодных поисков,
шиммер-плейсхолдеры бейджей вместо статичного «поиск…», разделение «пусто» и «упало» в боковой панели с
реальным действием повтора для второго случая) был предварён тремя независимыми консультациями
(дизайн/продукт/надёжность-и-обработка-ошибок) до написания кода, при реальных ограничениях на тот момент:
живого потокового вывода по каждому трекеру ещё не существовало (был только финальный `{results,
indexers}`), холодный поиск мог занимать до ~40 секунд, и две независимые асинхронные операции
(`poolStatus`/`seasonLoads[season]`) могли выполняться одновременно.

Продуктовые решения, реализованные буквально:

- **Один чистый селектор схлопывает независимые асинхронные операции в один пользовательский статус на
  сезон** (`selectSearchProgress`, порядок «худшее из двух»: loading побеждает error побеждает idle) —
  «готов ли именно ЭТОТ сезон» — единственный вопрос, который волнует пользователя, а не то, какая из двух
  операций сейчас выполняется. Фоновый ленивый повтор по сезону остаётся невидимым как отдельный статус —
  это автоматическая инфраструктура восстановления, а не веха, о которой стоит объявлять.
- **Никакого обратного отсчёта времени** — сырые «00:23» на медленном соединении выглядят как зависание;
  вместо этого текст ЭСКАЛИРУЕТ по фиксированному порогу в 15 секунд, от `'Ищем раздачи по всем трекерам…'`
  к `'Опрашиваем трекеры — некоторые отвечают медленно, обычно до 40 секунд'`.
- **Никакого автоматического повтора с backoff** — экран, самостоятельно меняющий состояние, пока внимание
  пользователя/курсор пульта может быть где-то ещё, дезориентирует на TV-интерфейсе с D-pad; повтор — всегда
  явное нажатие кнопки, там же, где уже была конвенция `message.retry`.

`selectSearchProgress(state)` — единственный источник истины «идёт ли поиск/упал ли он, и сколько это уже
длится», чистая производная над `poolStatus`/`seasonLoads[state.season]` плюс два новых
**чисто косметических** поля состояния без роли в устаревании (`poolGeneration` по-прежнему единственный
guard устаревания): `poolStartedAt` (таймстамп начала запроса, только для вычисления `elapsedMs`/`slow`) и
`poolAttempt` (счётчик «попытка N», для отображения). Спиннер — простой CSS `@keyframes`
(`.torrent-mod__spinner`), без картинок и анимационных библиотек. Поскольку эскалация текста зависит от
времени по часам, а не от единичного перехода состояния, небольшой `setInterval` (5с, активен только пока
`selectSearchProgress` сообщает `'loading'`) — то, что реально заставляет эскалацию появиться на экране.
Бейджи серий во время загрузки сезона стали шиммер-плейсхолдерами (`selectEpisodeBadges` возвращает
`{text, loading}` вместо голой строки) вместо текста «поиск…». Боковой пикер различает `status:'empty'` и
`status:'error'` (`selectPickerData`) — семантически противоположные вещи (ничего не существует против
приложение не смогло проверить), и только неудача заслуживает кнопки повтора (`retrySeasonLoad(season)`).

Отдельная мелочь той же линии: виджету статуса позже разрешили стать визуально выше (`padding`, не
`margin` — по той же причине collapse-safety, что и везде в этом проекте) под более длинный текст эскалации
и обратного отсчёта повтора; любой путь кода, меняющий высоту этого элемента, теперь явно вызывает
`Lampa.Layer.update()`, иначе закэшированная в `scroll.minus()` математика высоты снова протухла бы.

## Что мы сознательно не делаем, и почему

- **Полноценная система типов** (TypeScript или `// @ts-check` + `tsc`) — вошла бы в противоречие с
  рабочими паттернами (например, мутацией при скоринге) без более крупного рефакторинга, и добавила бы
  build-зависимость, которой проект избегал до появления esbuild ради бандлинга ES-модулей.
- **Закоммиченный/CI-gated тестовый набор** — существующий `npm run test:plugin` уже покрывает чистые
  функции и доменные smoke-сценарии; для codebase такого размера с одним автором и без амбиций стать
  общим фреймворком этого достаточно.
- **Runtime-библиотека схемной валидации** (в духе zod/ajv) на границах модулей — не потребовалась бы для
  закрытия ни одного из найденных реальных багов; добавила бы зависимость и косвенность без выгоды.
- **Блокетный `Object.freeze()`** на данных, пересекающих границы модулей — конфликтует с рабочим паттерном
  мутации в скоринге, который сознательно задокументирован, а не исправлен, поскольку риск сегодня нулевой.
- **Универсальная «guarded task»-обёртка** вместо `generation-guard.js` — то, что каждое место коммитит в
  стор при успехе, различается слишком сильно, чтобы протащить всё через одну форму без лишней косвенности.
- **Единый пакет playback-примитивов сразу вместе с доменными** — у `playback/smart-preload.js` нет
  открытого бага и нет тестового покрытия; переносить его в `shared/core/` стоит одним отдельным проходом
  с полной живой проверкой, а не размазывать по нескольким частичным миграциям.

Общая нить: каждый инструмент выше добавлен только там, где он закрывал уже найденный, конкретный, реальный
класс бага — не «на будущее» и не по общей методологической моде.
