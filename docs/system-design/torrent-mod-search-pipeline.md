# Как устроен поиск, скоринг и буферизация в Torrent Mod

Процессный документ: архитектура + почему она такая, включая то, что было проверено синтетическими
тестами, а не просто «должно работать по идее».

## Модель данных на кандидата

Каждая найденная раздача (`mapTorrent(raw)` в `TorrentModPlugin.js`) превращается в объект с полями из
двух источников:

- **Из ответа Jackett напрямую** (не разобрано регулярками, а взято как есть): `tracker`, `size`,
  `seeders`, `peers`, `publishedAt` (`raw.PublishDate`), `magnet`/`link`.
- **Разобрано из заголовка** регулярками (`parseRelease(title)`): сезон/диапазон серий (пак vs один
  эпизод — `explicitSeason`/`explicitEpisode`), `resolution`, `codec`, `hdr`, `audioChannels`,
  `voiceType`, `subtitles`, `is3d`, `year`.

Регулярки настроены на реальных заголовках, стянутых с живого инстанса Jackett этого проекта (RuTracker,
NoNaMe, BigFANGroup и т.п.), не выдуманы — при дрейфе точности тегов их и надо перенастраивать первыми.

### Найденный баг парсинга: `\bдубляж\b` никогда не матчится

JS `\b` определён через `\w` (`[A-Za-z0-9_]` — только ASCII), кириллица в `\w` не входит. Значит между
пробелом и «Д» границы слова не возникает вообще — `\b` там просто не с чем сформировать.
Подтверждено: `/\bдубляж\b/i.test('x264 Дубляж')` → `false`; `/дубляж/i.test(...)` → `true`. Остальные три
варианта перевода (Многоголосый/Одноголосый/Оригинал) не оборачивали свою кириллическую альтернативу в
`\b` — Дубляж был единственным несогласованным случаем. Реальные Дубляж-раздачи молча оставались без
метки перевода с момента написания этого регэкспа. **Правило на будущее: никогда не оборачивать `\b`
вокруг кириллической (или вообще не-ASCII) альтернативы в JS-регэкспе** — она просто никогда не
сматчится, без единой ошибки, которая бы на это указала.

## Гейт + скоринг: одна формула, не три раздельных числа

`scoreCandidate(item, target)` возвращает `{passes, matchScore, qualityScore, availabilityScore, value}`.

### `matchScore` — жёсткий гейт, не входит в ранжирование

`passesMatchGate(item, target)`:

- similarity названия < 0.34 → отказ.
- релиз явно называет сезон, и он не совпадает с целевым → отказ.
- целевая серия задана, релиз явно называет диапазон серий, целевая серия вне диапазона → отказ.
- иначе — проходит (в том числе релизы без явного сезона/серии — пропускаются дальше, пусть решает
  качество/доступность).

Кандидаты, не прошедшие гейт, **не участвуют в списке вообще** — не ранжируются ниже, не появляются даже
в пикере-фолбэке. Раздача с точным `S01E01` в заголовке, но от другого произведения, не должна быть
опцией никогда, сколько бы у неё ни было сидов.

### `qualityScore` — треугольный пик, не «чем больше, тем лучше»

```
reference = REFERENCE_BITRATE_MBPS[resolution] × (0.6 если codec === 'H.265', иначе 1)
deviation = |bitrateMbps − reference| / reference
qualityScore = max(0, 20 × (1 − deviation))
```

`REFERENCE_BITRATE_MBPS`: `2160p→18, 1080p→6, 720p→3, 480p→1.5` (грубые H.264-ориентировочные величины —
формула не требует точности, только что пик был примерно в нужном месте). HEVC вдвое эффективнее при том
же качестве, отсюда множитель `0.6` — иначе честно закодированный HEVC-релиз штрафовался бы за «слишком
низкий» битрейт.

Монотонная функция (было раньше: `min(20, bitrateMbps × 2.5)`) всегда отдаёт победу самому раздутому
ремуксу — не «лучше смотреть», а просто «больше файл». Пик решает это прямо.

`bitrateMbps` считается `estimateBitrateMbps`: `размер / episodes_covered / длительность_серии_из_TMDB`,
где `episodes_covered` — явный диапазон серий релиза, либо (для пака без явного диапазона) число серий в
сезоне. Это специально учитывает покрытие — иначе сезонный пак нечестно проигрывает синглу по «битрейту»
просто потому, что делит свой размер на всю пачку серий разом, а не на одну.

### `availabilityScore` — сиды и пиры одним логарифмом, пиры весомее

```
availabilityScore = min(24, log(seeders + peers × 1.5 + 1) × 6)
```

Пиры взвешены выше сидов сознательно — живой рой, который реально определяет скорость закачки, а не
просто «раздающие ничего не отдающие» сиды. (Было раньше: два раздельных капа `min(20,
log(seeders+1)×5) + min(8, log(peers+1)×2.5)` — сиды весили больше пиров, обратно тому, что нужно.)

### Итог

`value = qualityScore + availabilityScore` — `matchScore` уже сделал свою работу как фильтр, второй раз в
сумму не входит. Автоплей дополнительно требует `availabilityScore ≥ MIN_AVAILABILITY_FOR_AUTOPLAY (3)` —
идеальное совпадение по названию с пустым роем не должно автозапускаться, это зависание, а не «как
онлайн-сервис».

## Синтетическая проверка (не полагаемся на живой Jackett)

Живой агрегированный поиск Jackett периодически медленный/недоступен (наблюдалось многократно в течение
разработки — таймаут по ~25с). Чистые функции скоринга протестированы отдельным Node-скриптом на
синтетических кандидатах — 19 проверок, включая:

- гейт корректно исключает совпадающий по `SxxExx`-тегу, но чужой сериал, несмотря на огромный рой;
- гейт корректно исключает верный сериал, но не тот сезон;
- сезонный пак и одиночная серия дают одинаковый «на-серию» битрейт (учёт покрытия работает);
- раздутый ремукс проигрывает вменяемому энкоду по `qualityScore`;
- HEVC на половине референсного H.264-битрейта всё равно получает близкий к пиковому `qualityScore`;
- ноль сидов — кандидат гейт проходит (гейт про корректность, не про доступность), но
  `availabilityScore` около нуля (не пройдёт порог автоплея);
- пул кандидатов сезона матчит несколько разных серий одним и тем же пак-кандидатом;
- фильтр по переводу корректно сужает до серии-специфичного релиза, когда у пака другой перевод, и
  корректно возвращает пусто (не тихий фолбэк на весь пул), когда нужного перевода для конкретной серии
  нет вообще, хотя где-то в пуле он есть.

Скрипт — не часть репозитория (одноразовый харнесс в scratchpad), но сам факт и состав проверок стоит
знать: при следующей правке скоринга разумно воссоздать эквивалентный набор перед тем, как доверять
живому Jackett-тесту.

## Архитектура поиска: весь сезон один раз, не по клику на серию

См. [ADR-0005](../adr/0005-search-whole-season-once.md) за решением и альтернативами. Коротко:
`ensureSeasonPool()` запускает поиск по сезону в фоне при загрузке списка серий; результат обогащает
бейджи на строках серий, опции фильтров (только то, что реально нашлось) и делает клик по серии
мгновенным, когда пул уже её покрывает — иначе честный точечный поиск как раньше (recall safety net: у
пак-запроса ниже точность на конкретную серию, чем у `SxxExx`-специфичного).

## Playback и fallback

После выбора кандидата Torrent Mod не открывает native torrent screen и не ждёт
собственный duration-based buffer. Актуальный путь описан в
[`ADR-0003`](../adr/0003-no-global-player-patching.md):

```text
candidate
  → validate/reuse hash
  → POST /torrents action:add, если нужно
  → Torserver.files(hash), polling до file_stats
  → pickBestFile()
  → fire-and-forget &preload
  → Lampa.Player.play({url, url_reserve, playlist})
```

`url` — официальный прямой `Lampa.Torserver.stream(path, hash, fileId)`. Для
каждого файла также строится `url_reserve` на TorrServer GST/HLS:

```text
http://<torrserver>/gst/<hash>/master.m3u8?index=<fileId>&audio=0
```

Обычный direct stream используется первым. Если Lampa получает от `<video>`
фатальную ошибку декодирования/воспроизведения, её штатный обработчик уничтожает
текущий video element и один раз переключается на `url_reserve`. После этого
резерв удаляется. Дополнительной цепочки fallback'ов нет.

Для GST передаётся `hls_manifest_timeout: 60000`, поскольку прогрев GStreamer
может занимать около 20 секунд. Эти поля задаются как для верхнеуровневого
`Player.play(data)`, так и для каждого элемента `data.playlist`; иначе fallback
не пережил бы переход на следующую серию.

Preload следующего файла season-pack остаётся тихим оптимизационным шагом: при
примерно 85% текущей серии или за 60 секунд до конца отправляется `&preload`
для следующего playable-файла. Это не отдельный буферизационный экран и не
поллинг `/cache`.

### Границы fallback

- Простое зависание или бесконечная буферизация без fatal error не обязаны
  переключать поток на GST.
- Если GST тоже не работает, Torrent Mod не выбирает третий transport URL.
- Если выбранный файл не воспроизводится, другой файл той же раздачи автоматически
  не перебирается.
- `/ffp` и ffprobe не являются gate перед запуском: текущий playback доверяет
  реальному результату direct stream и штатному Lampa fallback.

Реальный direct → GST сценарий нужно проверять live на Lampa/WebOS: Node smoke-тесты
проверяют lifecycle и доменный flow, но не настоящий fatal error HTML5-видео.
