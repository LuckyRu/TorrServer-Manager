# Как устроен поиск, скоринг и буферизация в Torrent Mod

Процессный документ: архитектура + почему она такая, включая то, что было проверено синтетическими
тестами, а не просто «должно работать по идее».

## Модель данных на кандидата

Каждая найденная раздача (`mapTorrent(raw)` в `TorrentModPlugin.js`) превращается в объект с полями из
двух источников:

- **Из ответа Jackett напрямую** (не разобрано регулярками, а взято как есть): `tracker`, `size`,
  `seeders`, `peers`, `publishedAt` (`raw.PublishDate`), `magnet`/`link`.
- **Разобрано из заголовка** регулярками (`parseRelease(title)`): сезон/диапазон серий (пак vs один
  эпизод — `explicitSeason`/`explicitEpisode`), `resolution`, `codec`, `hdr`, `audioChannels`,
  `voiceType`, `translators`, `subtitles`, `is3d`, `year`.

Регулярки настроены на реальных заголовках, стянутых с живого инстанса Jackett этого проекта (RuTracker,
NoNaMe, BigFANGroup и т.п.), не выдуманы — при дрейфе точности тегов их и надо перенастраивать первыми.

### Диагностика парсинга

Каждая сырая запись получает отдельный лог `Torrent Mod [search]: metadata-parse: раздача` до
title-gate. В объекте лога видны исходный `title`, трекер, наличие magnet/link, размер, сиды/личеры,
дата публикации и весь результат `parseRelease`: сезоны, серии, качество, источник, HDR, кодек,
контейнер, перевод, студия, субтитры и compatibility. Поле `accepted` показывает, была ли запись
пригодна для доменного пула; `parseError` фиксирует исключение парсера. Поэтому по консоли можно
отдельно отличить «метаданные распознаны неверно», «нет ссылки на скачивание» и «раздача позже отброшена
title-gate».

### Найденный баг парсинга: `\bдубляж\b` никогда не матчится

JS `\b` определён через `\w` (`[A-Za-z0-9_]` — только ASCII), кириллица в `\w` не входит. Значит между
пробелом и «Д» границы слова не возникает вообще — `\b` там просто не с чем сформировать.
Подтверждено: `/\bдубляж\b/i.test('x264 Дубляж')` → `false`; `/дубляж/i.test(...)` → `true`. Остальные три
варианта перевода (Многоголосый/Одноголосый/Оригинал) не оборачивали свою кириллическую альтернативу в
`\b` — Дубляж был единственным несогласованным случаем. Реальные Дубляж-раздачи молча оставались без
метки перевода с момента написания этого регэкспа. **Правило на будущее: никогда не оборачивать `\b`
вокруг кириллической (или вообще не-ASCII) альтернативы в JS-регэкспе** — она просто никогда не
сматчится, без единой ошибки, которая бы на это указала.

## Гейт + скоринг: одна формула, не три раздельных числа

`scoreCandidate(item, target)` возвращает гейт, объяснимую оценку payload, отдельные составляющие
качества/доступности/риска и итоговый `value`.

### `matchScore` — жёсткий гейт + малый confidence-бонус

`passesMatchGate(item, target)`:

- similarity названия < 0.34 → отказ.
- релиз явно называет сезон, и он не совпадает с целевым → отказ.
- целевая серия задана, релиз явно называет диапазон серий, целевая серия вне диапазона → отказ.
- иначе — проходит (в том числе релизы без явного сезона/серии — пропускаются дальше, пусть решает
  качество/доступность).

Кандидаты, не прошедшие гейт, **не участвуют в списке вообще** — не ранжируются ниже, не появляются даже
в пикере-фолбэке. Раздача с точным `S01E01` в заголовке, но от другого произведения, не должна быть
опцией никогда, сколько бы у неё ни было сидов.

Прошедший гейт кандидат получает до 4 дополнительных баллов `matchConfidenceScore`. Это позволяет
точным season/episode-сигналам разбить близкие результаты, но не превращает match в повторный главный
вес.

### `estimatePayload` — размер всего торрента на оценённую длительность

```
payloadMbps = torrentSizeBytes × 8 / (estimatedDurationMinutes × 60 × 1_000_000)
```

Это не видеобитрейт: в `torrentSizeBytes` входят все аудиодорожки, субтитры и дополнительные файлы.
Результат несёт `confidence`, охват, длительность и причину. Неизвестная длительность фильма больше не
подменяется 42 минутами. Многосезонный пак без `E`-диапазона делится на сумму `episode_count` названных
сезонов; неоднозначные паки получают пониженную confidence.

### `qualityScore` — визуальная ценность, а не близость к «идеальному размеру»

База строится из resolution (`2160p=16, 1080p=12, 720p=7, 480p=3`), source (`Remux=4`,
`BDRip/WEB-DL=3`, `WEBRip=2`, `HDTV/HDRip=1`) и HDR (`+2`). Высокий payload никогда не уменьшает
quality. Низкий payload может дать до 8 штрафных баллов, но только пропорционально confidence.

### `availabilityScore` — сидеры первичны, Jackett Peers являются leechers

```
seeders == 0 → 0
иначе min(20, ln(seeders + 1) × 5) + min(2, ln(leechers + 1) × 0.4)
```

Личеры показывают спрос и могут отдать части файла, но не гарантируют полную копию. Поэтому они дают
не более 2 баллов и не создают доступность без сидеров.

### `streamingRiskPenalty` — тяжёлому потоку нужен более устойчивый swarm

До регистрации торрента реальная скорость неизвестна. Консервативный proxy:

```
requiredSeeders = max(3, payloadMbps × 1.25)
penalty = 8 × (1 − seeders / requiredSeeders) × confidenceWeight
```

Штраф применяется только при `high`/`medium` confidence и только ниже requiredSeeders. Он нужен, чтобы
1080p с большим устойчивым swarm мог обойти тяжёлую 4K-раздачу с небольшим запасом по сидерам.

### `pipelinePenalty` — риск серверного GST, не браузерных кодеков

`RAW DVD=8`, `AV1=3`, остальные legacy-кодеки/контейнеры `=5`. Машина может транскодировать их, поэтому
это мягкий риск стоимости/надёжности пайплайна, а не запрет.

### Итог

`value = qualityScore + availabilityScore + matchConfidenceScore - streamingRiskPenalty - pipelinePenalty`.
Автоплей требует минимум 3 сидера, `matchScore ≥ 40` и `availabilityScore ≥ 4`.

## Синтетическая проверка (не полагаемся на живой Jackett)

Живой агрегированный поиск Jackett периодически медленный/недоступен (наблюдалось многократно в течение
разработки — таймаут по ~25с). Чистые функции скоринга протестированы отдельным Node-скриптом на
синтетических кандидатах — 19 проверок, включая:

- гейт корректно исключает совпадающий по `SxxExx`-тегу, но чужой сериал, несмотря на огромный рой;
- гейт корректно исключает верный сериал, но не тот сезон;
- многосезонный пак без диапазона делится на сумму TMDB episode counts;
- фильм без runtime получает `payloadMbps=null`, а не выдуманные 42 минуты;
- высокий H.264 payload не уменьшает visual quality;
- HEVC/HDR со здоровым swarm выигрывает живой Clarkson's Farm сценарий;
- 1080p/106 сидов выше 4K/13 сидов из-за риска непрерывной буферизации;
- ноль сидов — кандидат гейт проходит (гейт про корректность, не про доступность), но
  `availabilityScore` строго ноль независимо от личеров;
- пул кандидатов сезона матчит несколько разных серий одним и тем же пак-кандидатом;
- фильтр по переводу корректно сужает до серии-специфичного релиза, когда у пака другой перевод, и
  корректно возвращает пусто (не тихий фолбэк на весь пул), когда нужного перевода для конкретной серии
  нет вообще, хотя где-то в пуле он есть.

Скрипт — не часть репозитория (одноразовый харнесс в scratchpad), но сам факт и состав проверок стоит
знать: при следующей правке скоринга разумно воссоздать эквивалентный набор перед тем, как доверять
живому Jackett-тесту.

## Архитектура поиска: progressive whole-work pool

При входе создаётся одна parallel-search job по названию произведения. Plugin Hub опрашивает каждый
индексатор отдельно, а клиент мержит ответы в `state.pool` в порядке их завершения. Поэтому здесь
важно различать два понятия:

- **данные доступны** — в pool уже есть прошедший гейт кандидат;
- **поиск завершён** — `poolStatus === 'ready'`, то есть ответили все индексаторы.

Второе не является gate для первого. Фильм показывает список после первого полезного ответа и
обновляет его по мере роста pool. Клик серии проверяет текущий pool до проверки `poolStatus` и
запускает готового кандидата немедленно. Если совпадения ещё нет, запоминается последний click intent;
store subscription повторяет его на следующем изменении pool. Старый 400-миллисекундный polling,
который ждал финального `ready`, удалён.

Смена сезона фильтрует whole-work pool локально. Только если полностью завершившийся title-пул не
содержит кандидатов выбранного сезона, запускается ленивая сезонная дозагрузка (`Имя Sxx` +
`Имя N сезон`) с мержем результата обратно в общий pool.

## Playback и fallback

После выбора кандидата Torrent Mod не открывает native torrent screen и не ждёт
собственный duration-based buffer. Актуальный путь описан в
[`ADR-0003`](../adr/0003-no-global-player-patching.md):

```text
candidate
  → немедленно смонтировать native Player shell + видимый status overlay (без media URL)
  → validate/reuse hash
  → POST /torrents action:add, если нужно
  → Torserver.files(hash), polling до file_stats
  → pickBestFile()
  → fire-and-forget &preload cache nudge
  → GET /gst/{hash}/probe?index={fileId}
  → handoff без detach в Lampa.Player.play({GST url with audio=N, voiceovers, playlist})
  → снять status overlay по Player.ready
```

Единственный player transport — TorrServer GST/HLS. После probe выбранной дорожке передаётся её
настоящий индекс:

```text
http://<torrserver>/gst/<hash>/master.m3u8?index=<fileId>&audio=<trackIndex>
```

На экране результатов список для меню «Студия» — производная от `state.pool`: селектор собирает из
распарсенных релизов уникальные студии в порядке появления. В state хранится только пользовательский выбор
`state.filters.translator`, который персистится глобально и по `movie.id`, как остальные фильтры.
Раздача с несколькими студиями проходит при выборе любой из них.

Если для сериала и сезона сохранено предпочтение студии, оно сопоставляется с metadata нового
файла; иначе выбирается первая audio-дорожка. Список передаётся в `voiceovers` всегда. Прямой
browser stream и `url_reserve` больше не строятся.

Для первого файла верхнеуровневый lazy URL недоступен в Lampa, поэтому ранний Player shell
монтируется через публичный `Player.render()`. Он не получает фиктивный URL: обязательный probe
по-прежнему идёт раньше любого media/GST task. Внутренние панели Lampa до `play()` скрыты, поэтому
видимость ожидания обеспечивает plugin-owned overlay внутри того же Player DOM. При handoff DOM не
отсоединяется, а overlay живёт до `Player.ready`. Back уничтожает player lifecycle scope. Каждый
выбранный файл получает дочерний scope, которому принадлежат probe/retry и file-specific listeners;
переход серии уничтожает старый file scope, но сохраняет Player session. Временный сбой probe
повторяется один раз, 4xx/unsupported container считается детерминированным.

Для GST передаётся `hls_manifest_timeout: 60000`. Для следующей серии playlist содержит lazy
URL-функцию: перед запуском она делает такой же probe, заполняет `voiceovers` и только затем
передаёт Lampa готовый GST URL.

Preload следующего файла season-pack остаётся тихим оптимизационным шагом: при
примерно 85% текущей серии или за 60 секунд до конца отправляется `&preload`
для следующего playable-файла. Это не отдельный буферизационный экран и не
поллинг `/cache`.

### Границы fallback

- Если GST не отвечает или не находит audio-дорожку, media source не запускается, ранняя оболочка
  Player закрывается; на direct stream Torrent Mod не переключается.
- Если GST тоже не работает, Torrent Mod не выбирает третий transport URL.
- Если выбранный файл не воспроизводится, другой файл той же раздачи автоматически
  не перебирается.
- `/gst/.../probe` — обязательный gate перед каждым стартом файла; `/ffp` не используется.

GST-first сценарий нужно проверять live на Lampa/WebOS: Node-тесты проверяют нормализацию metadata
и доменный flow, но не реальный GStreamer pipeline.
