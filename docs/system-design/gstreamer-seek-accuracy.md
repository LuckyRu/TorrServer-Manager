# Точность перемотки в GStreamer-пайплайне

Статус: реализовано в форке TorrServer (`external/TorrServer`, ветка `torrserver-manager`). Точная
перемотка работает для Matroska и для всех транскодируемых форматов; MP4/MOV в режиме passthrough
остаётся приблизительным — см. [«Что осталось»](#что-осталось).

Документ описывает, **почему** перемотка устроена именно так. Знание досталось двумя итерациями по
живым логам, и без него код выглядит произвольным: непонятно, отчего к `ACCURATE` нельзя добавить
`KEY_UNIT`, зачем обрезка стоит в разных местах пайплайна и почему наружу отдаётся не та позиция,
которую вернул сам GStreamer.

Связанные документы:

- [API плеера Lampa](../reference/lampa-player-api.md);
- [устойчивость GStreamer-пайплайна](gstreamer-pipeline-robustness.md);
- [ADR-0006: нативный фолбэк вместо ffprobe-гейта](../adr/0006-native-player-fallback-not-ffprobe-gate.md).

## Два разных вопроса, которые легко перепутать

Исходно в коде стояло `accurate := r.task.Cue != nil`, и это склеивало два независимых вопроса:

1. **Есть ли индекс keyframe'ов?** Нужен, чтобы нарезать HLS-сегменты по опорным кадрам. Строится
   только для Matroska (`readMatroskaCueTimeline`).
2. **Можно ли отдать кадр ровно с запрошенной позиции?** Зависит не от индекса, а от того,
   декодируем ли мы поток покадрово.

Из-за склейки перемотка молча становилась приблизительной везде, кроме MKV. На живом AVI-паке это
давало промах **+5.5 с** при запросе 906 с и одиннадцать секунд ожидания: демиксер уезжал на
следующий keyframe исходника, а плеер пытался компенсировать откатами назад.

Сейчас вопросы разведены:

| Вопрос | Где отвечает | Условие |
|---|---|---|
| нарезать сегменты по keyframe'ам | `shouldUseCueTimeline` | Matroska **и** кодек не транскодируется |
| просить точную позицию | `Task.seekCanBeAccurate` | есть Cue **или** видео транскодируется |

`seekCanBeAccurate` возвращает `true` под транскодом, потому что там декодируется каждый кадр, а
энкодер сам ставит опорный кадр на границе сегмента (`key-int-max = fps × SegmentSeconds`). Доехать
до точного кадра не стоит ничего сверх уже выполняемой работы.

При passthrough кадры копируются как есть — начать поток можно только с keyframe исходника, поэтому
без индекса точность просить бессмысленно: демиксер всё равно отдаст опорный кадр.

## Матрица форматов

| Контейнер | Демиксер | Режим по умолчанию | Cue | Перемотка |
|---|---|---|---|---|
| Matroska / WebM, H.264/H.265/AV1/VP9 | `matroskademux` | passthrough | есть | точная |
| Matroska / MP4, прочие кодеки | по контейнеру | транскод | нет | точная |
| AVI | `avidemux` | транскод (`TranscodeAVI`) | нет | точная |
| MP4 / MOV, H.264/H.265/AV1/VP9 | `qtdemux` | passthrough | нет | **приблизительная** |
| ASF / WMV, FLV | `asfdemux` / `flvdemux` | транскод | нет | точная (вживую не проверено) |
| любой HDR→SDR | — | транскод | нет | точная |

Строки «прочие кодеки» и ASF/FLV раньше не играли вовсе: MPEG-4 ASP (DivX/Xvid), MPEG-2, MJPEG,
VC-1, WMV3 и VP6 дают пустой caps, считались копируемыми, а ветки копирования для них не
писалось — пайплайн собирался без видеодорожки. Исправлено правилом «не ремуксируем —
транскодируем» ([§0](gst-pipeline-plan-architecture.md#0-правило-не-ремуксируем--транскодируем),
живая проверка на MPEG-2 в MKV — [§9](gst-pipeline-plan-architecture.md#9-живая-проверка-правила-0));
перемотка у них точная, потому что транскод декодирует каждый кадр.

Индексы `idx1` (AVI) и Simple Index Object (ASF) реализовывать **не нужно**: эти форматы всегда идут
через транскод, где индекс исходника не описывает выходной поток.

## Флаги перемотки несовместимы между собой

```go
func videoSeekFlags(accurate bool) int32 {
    if accurate {
        return gstSeekFlagFlush | gstSeekFlagAccurate
    }
    return gstSeekFlagFlush | gstSeekFlagKeyUnit | gstSeekFlagSnapAfter
}
```

`KEY_UNIT` со `SNAP_AFTER` требуют «встать на ближайший keyframe **после** позиции», `ACCURATE` —
«отдать кадр ровно на позиции». Это противоположные требования, и вместе побеждают первые два.

Пока они стояли всегда, включение `ACCURATE` не меняло ничего — в логе было честное
`accurate=true` при промахе в пять секунд. Для Matroska ошибка не проявлялась: границы сегментов
там берутся из индекса и сами лежат на keyframe'ах, поэтому `SNAP_AFTER` никуда не сдвигал.

**Ловушка:** флаги нельзя «добавлять для надёжности». Набор либо один, либо другой.

## Обрезка: где именно и почему в разных местах

Точная перемотка ставит демиксер на опорный кадр **перед** целью — кадры между ним и целью нужны
декодеру, но зрителю уже показаны. Их снимает PTS-барьер (`segmentClipPadProbe`: дропает буферы с
`PTS < segmentStart`).

Барьеров три, и место каждого принципиально:

| Дорожка | Режим | Точка | Почему именно там |
|---|---|---|---|
| видео | passthrough | `video_timestamper` src | кадры копируются, лишнее снимается после таймстемпера |
| видео | транскод | `video_encoder` **sink** | энкодер должен получить первым кадр ровно с запрошенной позиции и сделать его опорным |
| аудио | оба | `audio_clipper` (`aacparse`) src | последняя общая точка перед `mp4mux` для copy и transcode |

Две ошибки, которые здесь уже совершались:

- **Обрезать видео после энкодера.** Тогда сегмент начнётся с кадра, которому нужен выброшенный
  keyframe, — декодер клиента не сможет его открыть.
- **Обрезать только видео.** `ACCURATE` сдвигает назад **обе** дорожки: аудио приезжает с той же
  ранней шкалой. Без барьера на звуке ранние аудиофреймы попадают в mux, и после перемотки звук
  опережает картинку на длину GOP.

## Наружу отдаётся не та позиция, что вернул GStreamer

```go
func (r *gstRunner) seekPositionAfter(pipeline uintptr, requestedSeconds float64, accurate bool) float64 {
    position := r.querySeekPosition(pipeline, requestedSeconds)
    if accurate && position < requestedSeconds {
        return requestedSeconds
    }
    return position
}
```

`elementQueryPosition` возвращает позицию **демиксера**, то есть точку *до* обрезки. Отдать её
наружу — соврать назад на длину GOP: сегменты начнут строиться раньше запрошенного, и плеер получит
уже показанное. В логах это выглядело как `requested=660.000s actual=657.621s`.

Сдвиг **вперёд** сохраняется как есть: поток действительно начнётся там.

## Шкала сегментов после перемотки

Позиция наружу — одно, метки времени внутри сегментов — другое. `mp4mux` начинает свою шкалу с
первого кадра, который **до него дошёл**, а `mp4BoxReader` прибавляет к ней смещение
(`SetTimelineOffsetNS`), чтобы `tfdt` совпал со шкалой плейлиста. Смещение брали из пробы на
`mq.src_0` — это первый кадр **демиксера**, тот самый опорный кадр перед целью, который барьер потом
выбрасывает. Каждый сегмент после перемотки получал метку раньше своего места в плейлисте ровно на
расстояние до опорного кадра — у Matroska это длина предыдущего cue-сегмента, до 10 с.

Касалось любой точной перемотки: перемотки пользователем, восстановления после ошибки и
**разморозки сессии после паузы**. Замер на живой раздаче (HEVC в MKV, cue-режим):

| | плейлист | было `tfdt` | стало `tfdt` |
|---|---:|---:|---:|
| перемотка на сегмент 42 | 158.700 | 154.655 | 158.700 |
| перемотка на сегмент 28 | 115.824 | 105.814 | 115.824 |
| разморозка на сегменте 42 | 158.700 | 154.655 | 158.700 |
| транскод, перемотка на 162 с | 162.000 | 158.700 | 162.000 |

Почему это долго не было видно: hls.js 1.4.7 в passthrough пересчитывает `initPTS`, если начало
фрагмента расходится с плейлистом больше чем на длину самого фрагмента («Adjusting initPTS»). Сдвиг
больше длины сегмента он молча исправлял; сдвиг меньше — проходил насквозь, и зритель терял эти
секунды. Плееры, которые верят `tfdt` (нативный HLS), получали сдвиг целиком: после выхода из паузы
в логе запросы K → K+3 → K+2, недокачанная дыра на месте K+1 и вставшее воспроизведение.

**Сделано:** шкала берётся от первого кадра, прошедшего видеобарьер (`segmentClipProbeState.
firstFrameNS`). Без барьера — прежний кадр демиксера, там ничего не выбрасывается.

**Ловушка:** на passthrough барьер стоит после `h264timestamper`/`h265timestamper`, а они сдвигают
метки буферов и сегмент на 1000 часов, чтобы DTS не уходил в минус. Метка буфера там — не время
потока. Первая версия исправления взяла её как есть и получила шкалу 3 600 000 с. Правильно —
перевести через SEGMENT-событие того же пада: `pts − start + time`. На случай, если перевод всё же
сломается, `applyPendingVideoStart` не принимает первый кадр вне окна «опорный кадр … цель + сегмент»
и пишет ошибку в лог вместо шкалы, уехавшей на часы.

**Остаток:** после свежего пайплайна (разморозка, путь `reuse=false`) таймстемпер оценивает глубину
переупорядочивания в 5 кадров вместо 2, и DTS следующих сегментов идёт на 0.125 с раньше. PTS
точные, для hls.js сегменты непрерывны.

## Замеры

Живой AVI-пак (сериальная раздача BDRip, транскод в H.264), запрос перемотки на 906 с:

| | до | после |
|---|---:|---:|
| фактическая позиция | 911.5 с (+5.5) | в пределах кадра |
| ожидание | 11 с | доли секунды |

Промежуточное состояние (разведённые флаги, но обрезка только для passthrough) давало сдвиг
**назад**: `660 → 657.6`. Это хуже исходного промаха вперёд — плеер получал уже показанное.

## Тесты

`server/gstreamer/seek_accuracy_test.go`:

- `TestSeekCanBeAccurate` — матрица «контейнер × режим» → точность;
- `TestSeekAccuracyFollowsTranscodeNotContainer` — признак идёт от транскода, а не от контейнера;
- `TestVideoSeekFlags` — наборы флагов взаимоисключающие;
- `TestSeekPositionNeverGoesBackWhenAccurate` / `TestSeekPositionKeepsForwardDrift` — позиция наружу.

`server/gstreamer/video_probe_gst_test.go`:

- `TestVideoClipProbeRecordsFirstFrameThroughTheBarrier` — барьер запоминает первый пропущенный
  кадр во времени потока, со сдвигом таймстемпера на 1000 часов;
- `TestSeekTimelineStartsAtFirstFrameIntoTheMux` — шкала от этого кадра, а не от опорного (на
  прежнем коде даёт 154.655 вместо 158.700);
- `TestSeekTimelineRejectsFirstFrameOutsideTheSeekWindow` — шкала за пределами окна не принимается.

Живой прогон эти тесты не заменяют: они фиксируют решения, а не поведение GStreamer. Проверка —
перемотка на реальной раздаче с чтением `seek requested`/`seek completed` из лога сервера и строка
`video seek start requested=… actual=… timeline=…`: `timeline` должен совпасть с `requested`.
Для шкалы оракул — сами сегменты: скачать `seg/N.m4s` той же сессии и сравнить `tfdt` первого
`traf` с суммой `#EXTINF` плейлиста до сегмента N.

## Что осталось

**MP4/MOV в passthrough.** Единственный формат без точной перемотки. Включать `ACCURATE` здесь
нельзя: кадры копируются, произвольная позиция физически недостижима. Нужен индекс keyframe'ов —
разбор `stss` из `moov` по образцу `cue.go` (там 467 строк EBML-разбора с чтением по HTTP-range из
торрента). Для MP4 объём сопоставим: найти `moov` (может лежать и в конце файла), разобрать
`stss`/`stts`/`ctts`, собрать `CueTimeline`.

Делать имеет смысл, только если MP4/MOV реально встречаются в раздачах: MKV и AVI уже точные.

## Знание о форматах размазано

Решения по контейнеру и кодеку принимаются в **семи** местах с частично пересекающейся логикой.
Именно их рассогласование породило обе ошибки выше — точность включили там, где обрезка не
стояла. Полный список мест, доказательства ещё двух живых дефектов и целевая модель (решение
считается один раз и становится значением `Plan`, а не переоткрывается каждым потребителем) —
[архитектура плана пайплайна](gst-pipeline-plan-architecture.md).

До перехода на неё любое изменение в одном месте требует проверки остальных шести.
