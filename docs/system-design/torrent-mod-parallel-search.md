# Параллельный поиск по трекерам и lifecycle scope в Torrent Mod

Процессный документ: архитектура + почему она такая. Отдельно — реальная история одной
архитектурной коррекции границы View/Domain, разобранная подробно, потому что урок из неё
переиспользуется, а не только вывод.

## Мотивация

До этой переделки поиск раздач шёл одним блокирующим запросом: Plugin Hub дергал агрегатный
эндпоинт Jackett `indexers/all/results`, который сам параллелит запрос по индексаторам на своей
стороне, но отвечает только когда отработал **самый медленный** из них. Один зависший или
деградировавший трекер держал в ожидании результаты всех остальных, уже готовых.

Пользователь прямо запросил архитектурную переделку, а не точечный фикс — после серии багов с
восстановлением после сбоя поиска ("при запуске плагина... должен быть спроектирован и
использоваться лайфскоуп объект для регистрации в нём всех асинхронных задач... и уберём паузу
между ретраями... сделай мне пул параллельных запросов по каждому трекеру"). Два независимых
запроса были реализованы вместе, потому что второй делает выгоду первого видимой:

1. **Общий lifecycle scope** — один объект, в который регистрируется каждый асинхронный ресурс
   экрана результатов (таймеры, подписки на store, произвольные cleanup-колбэки), чтобы один
   `dispose()` гарантированно снёс всё разом.
2. **Параллельный запрос по каждому трекеру** — вместо одного блокирующего вызова к агрегату
   Jackett, свой job-протокол на бэкенде, который стартует запрос к каждому индексатору отдельно
   и отдаёт результаты клиенту по мере готовности.

### Предыстория: лестница ретраев для целого агрегата (позже сокращена)

Ещё до параллельного поиска уже существовал автоматический ретрай на случай полного отказа
поиска — реальный инцидент ("Менталист 2008" дважды подряд падал целиком, единственным способом
восстановления было закрыть экран и открыть плагин заново) привёл к `POOL_RETRY_DELAYS_MS =
[3000, 6000, 12000, 20000]` (4 автоматических попытки с растущей задержкой, 5 попыток всего) с
живым посекундным countdown в статусной строке — здесь countdown осознанно **не** избегается
(в отличие от другого соседнего решения не показывать таймер для эскалации "медленного" поиска):
там время сетевое и непредсказуемое, тут таймер собственный `setTimeout`, поэтому посекундный тик
точен, а не вводит в заблуждение.

После перехода на параллельный поиск по трекерам эта лестница **сократилась с четырёх шагов до
двух** (`[3000,6000,12000,20000]` → `[5000,15000]`) — не откат требования "ретраи обязательны", а
изменение того, что теперь вообще значит "отказ": при параллельном опросе путь
ретрая/отказа целого пула срабатывает только когда **ни один** сконфигурированный индексатор не
ответил вообще (настоящий сбой — Jackett не поднят, либо разом отказали все трекеры), а не когда
подвис один из многих. Это заметно более редкий и более настоящий случай отказа, чем раньше,
поэтому прежняя агрессивная четырёхшаговая лестница ему больше не нужна.

## Lifecycle scope: одна точка регистрации асинхронных ресурсов

`shared/core/lifecycle.js`'s `createLifecycle()` вырос из голого флага `{isAlive, dispose}` в
настоящий реестр:

- `track(dispose)` — регистрация произвольного cleanup-колбэка, возвращает `untrack`;
- `setTimeout(fn, ms)` / `setInterval(fn, ms)` — таймеры, принадлежащие scope: обычный
  `setTimeout` сам снимается с учёта после срабатывания, оба типа таймеров гарантированно
  отменяются при `dispose()`;
- `subscribe(store, listener)` — подписка на store с автоматической отпиской при `dispose()`.

`dispose()` прогоняет все зарегистрированные cleanup в **обратном порядке регистрации**, каждый —
в собственном `try/catch`, чтобы упавший cleanup не заблокировал остальные.

Это напрямую заменило два независимых, вручную поддерживаемых метода `destroy()` —
`episodes-interactor.js` свой, `selection-interactor.js` свой — каждый из которых нужно было
руками обновлять при добавлении нового таймера или подписки. Именно этот риск ("N раздельно
запоминаемых `destroy()`") ранее уже был назван в другом месте кодовой базы (`shared/core/`) как
класс проблемы, который стоит закрыть один раз общим механизмом. Оба interactor-а лишились
собственных `destroy()` (и записей `destroy: destroy` в возвращаемом API) сразу же, как только
все их таймеры переехали на `scope.setTimeout`/`scope.track` — чистить вручную стало нечего.

View (`ui/results-screen.js`) регистрируется **в тот же самый** shared scope, не в свой:
единственная подписка `store.subscribe(render)` и `setInterval` статусного тикера (эскалирующий
countdown прогресс-виджета поиска) оба переехали на `domain.scope.subscribe`/
`domain.scope.setInterval`. `torrent-mod-component.js` уже вызывает `viewModel.destroy()` (→
`domain.destroy()` → `scope.dispose()`) **до** `view.destroy()` — так что к моменту, когда
собственный `destroy()` View отрабатывает, и domain, и scope уже снесены; ему остаётся только
View-специфичное DOM/jQuery-состояние (панель пикера, два инстанса `Lampa.Scroll`,
`explorer.destroy()`), которое никогда и не было заботой scope.

`results-domain.js`'s `destroy()` теперь — это просто `scope.dispose()`, с логированием на
идемпотентность (повторный вызов — задокументированный no-op, не тихо проглатывается).

## Протокол на бэкенде: job-based API вместо одного блокирующего вызова

`Services/PluginHub.cs` заменил единственный `GET /api/torrent-search` (агрегатный
`indexers/all/results` Jackett, один round-trip, ограниченный самым медленным индексатором) на
протокол из трёх эндпоинтов:

- **`GET /api/torrent-search/start?query=...&indexers=id1,id2&exclude=id3,id4`** → `{jobId, totalIndexers}`.
  Получает актуальный
  список сконфигурированных индексаторов через Torznab-капабилити Jackett
  (`t=indexers&configured=true`), затем запускает по одному `SearchOneIndexerAsync` на индексатор
  через `Task.Run`. Завершённый список не кэшируется: изменения индексаторов, сделанные в UI
  Jackett, видны уже в следующем поиске. Одновременные запросы делят только текущий in-flight
  запрос к Jackett и не используют устаревший снимок.
- **`GET /api/torrent-search/poll?jobId=...`** → `{done, indexers:[{id,name,ok,error,elapsedMs,
  results}]}`. Всегда отдаёт **полный накопленный** на текущий момент набор — polling
  stateless на клиенте, курсор "с прошлого опроса" не нужен.
- **`GET /api/torrent-search/cancel?jobId=...`** — best-effort. Настоящий backstop —
  `CleanupStaleSearchJobs`, TTL-развёртка каждые 3 минуты, выполняемая в начале каждого `/start`,
  на случай запроса на отмену, который вообще не пришёл (страница закрыта, обрыв сети).

### `cancel` — GET, а не POST

Первая реализация использовала POST и живьём упёрлась в `HttpListener` `411 Length Required`:
собственный HTTP-листенер .NET требует `Content-Length` у любого POST независимо от того, читает
ли обработчик тело — а этому эндпоинту читать нечего. GET снимает вопрос о теле POST-запроса и
`Content-Length` целиком, для действия настолько некритичного к методу.

### Найденная на этапе проектирования (не живьём) ловушка C#

Обработка завершений по индексаторам сделана через `Task.WhenAny` в цикле над
материализованным `.ToList()` списка задач, а **не** через `foreach (var t in tasks) await t`.
Второй вариант обрабатывает результаты в **исходном порядке списка**, независимо от того, какая
задача реально завершилась первой — что незаметно свело бы на нет весь смысл переделки
(показывать результаты самого быстрого трекера первыми), при этом код компилируется и
исполняется без единой видимой ошибки. Поймано на этапе проектирования, не на живом баге — стоит
запомнить как общую ловушку C#: последовательный `await` внутри `foreach` по списку задач —
ошибка корректности всегда, когда важен порядок "по мере завершения", а не просто дело вкуса.

### Проверено вживую до написания JS-кода

Curl-ом против реального Jackett-инстанса этого проекта, все три эндпоинта: `/start` вернул 5
реальных сконфигурированных индексаторов (anilibria/bigfangroup/megapeer/noname-club/
rutracker-ru); `/poll` вернул реальный тайминг по каждому индексатору (4–36 мс в этом прогоне —
сам Jackett агрессивно кэширует, так что эти цифры занижают то, что покажет по-настоящему
холодный многотрекерный поиск); `/cancel` корректно сделал последующий `/poll` 404.

## Клиентский модуль параллельного поиска

`search/transport/parallel-search.js` (новый файл) — единственный модуль, который реально говорит с тремя
эндпоинтами. Обычный GET-polling через существующий хелпер `request()` (`shared/utils.js`, сам
построен на `Lampa.Reguest`), **осознанно не** `fetch()`/`ReadableStream`-стриминг — та же
осторожность "целевое устройство — браузер LG WebOS TV, транспорт должен быть простым", что и в
остальных транспортных решениях этого плагина.

`startParallelSearch(query, onIndexerResult, onDone, scope)` возвращает `{cancel}`; если передан
`scope`, таймер опроса регистрируется в нём — уход с экрана результатов посреди поиска
автоматически останавливает клиентский polling-цикл, без отдельного шага очистки, о котором
вызывающий код обязан помнить.

### Найденный при разработке (не по живому репорту) баг дублирующей доставки

`/poll` всегда отдаёт **полный** накопленный список индексаторов (так и задумано, для
stateless-клиента) — первая версия `startParallelSearch` на **каждом** тике опроса скармливала
в `onIndexerResult` каждую запись из этого списка, так что уже отчитавшийся индексатор
передоставлялся заново примерно каждые 600 мс, до самого завершения job, а собственный
аккумулятор вызывающей стороны (`poolIndexers.concat([...])`) не имел способа понять, что видит
один и тот же индексатор второй раз — растущий список задублированных записей в виджете, не
падение, но настоящий баг. Исправлено множеством `delivered`, ключ — `entry.id`, внутри самого
`startParallelSearch`: запись каждого индексатора пересекает границу `onIndexerResult` ровно один
раз за весь поиск.

### Внешний контракт не изменился

`search-backend.js`'s `searchTorrentMod`/`searchTorrentModProgressive` переписаны на использование
этого транспорта внутри, но их **внешний** контракт остался побайтово тем же самым (`{results,
indexers, failed}` для Promise-based `searchTorrentMod`; новый `searchTorrentModProgressive` с
парой колбэков `onIndexerResult`/`onDone` — специально для поиска целого whole-work pool). Именно
поэтому ленивая дозагрузка сезона (`ensureSeasonLoaded`) и повтор поиска после ошибки
получили выигрыш в скорости параллельного запроса **бесплатно**, без единой
правки кода — переехать на новый прогрессивный вариант понадобилось только `loadAllTorrents` (той
единственной точке вызова, которой реально нужны прогрессивные, по-трекерно обновления, а не
просто более быстрый одиночный Promise).

Ленивая дозагрузка конкретного сезона выполняется ровно один раз на попытку: пустой ответ
помечает сезон как `ready`, ошибка — как `error`, без фонового повтора через таймер. Повтор
сезонного запроса запускается только явным `retrySeasonLoad(season)` из UI; автоматические
повторы остаются только у initial whole-work поиска.

### Структурное следствие: `state.pool` больше не бывает `null`

`state.pool` (`results-state.js`) сменился с nullable (`null` до первого успешного поиска) на
**всегда массив** — прямое структурное следствие того, что поиск стал прогрессивным: "ещё не
устоялось" и "по-настоящему пусто" теперь оба представимы как `[]`, различаются только полем
`poolStatus`. Это тот же аргумент, который раньше уже звучал defensively при разборе краша
`selectPickerData` на `null`-пуле — но теперь сделан структурным, а не полагающимся на то, что
каждый будущий вызывающий код не забудет проверку. `selectEpisodeBadges`/`selectPickerData`
(`results-selectors.js`) теперь сперва проверяют "у этой серии уже есть настоящие кандидаты",
и только потом смотрят на loading/error — серия может иметь подтверждённое совпадение от быстрого
трекера, пока другие, более медленные, ещё не ответили, и показывать плейсхолдер загрузки поверх
уже пришедших данных воссоздало бы ту самую боль ожидания, ради устранения которой всё это
переделывалось.

### Ручной поиск отменяет всё, что осталось от предыдущего

При повторном запуске поиска после ошибки `episodes-interactor.js`'s `requery()` вызывает
`poolSearchHandle.cancel()` перед стартом нового поиска —
best-effort уведомляет `PluginHub.cs` о необходимости прервать ещё не завершённые запросы старого
поиска по индексаторам через тот же эндпоинт `/cancel`, которым уже пользуется штатное закрытие
экрана, а не просто прекращает клиентский polling.

### Тесты потребовали реальной переработки, не только новых кейсов

Все существующие smoke-тесты мокали старый единственный `/api/torrent-search` — сам харнесс
(`test/helpers/mock-lampa.mjs`) расширили так, чтобы он транслировал старую форму регистрации
мока "один вызов на поиск" в новый трёхэндпоинтовый протокол под капотом, поэтому ~30 существующих
мест вызова в `smoke.test.mjs` не потребовали изменений вообще — синтетическая job/`Map` внутри
мока отдаёт данные совпавшего обработчика на первом же `/poll`, обёрнутые как одна запись
индексатора.

Найден реальный флейк, не теоретический: двухшаговый протокол добавляет настоящий лишний
сетевой прыжок на поиск по сравнению со старой однозаходной моделью, и первая версия мока
резолвила даже фикстуру с `delay: 0` через `setTimeout(fn, 0)` на **обеих** ногах — два прыжка
макротаска там, где старый мок нуждался только в одном, изредка превышая бюджет
`flushMicrotasks()` в 10 мс сьюта под реальным джиттером event loop и роняя тесты, вообще не
имеющие отношения к самой фиче. Исправлено резолвом через микротаск (`Promise.resolve().then(fn)`)
вместо настоящего таймера всякий раз, когда задержка фикстуры falsy — мок с нулевой задержкой
снова становится ровно таким же быстрым, как старая однопрыжковая версия, а по-настоящему
запрошенная задержка (гонки/staleness-тесты этого сьюта) по-прежнему идёт через реальный таймер.

Заодно нашли и исправили, гоняясь за внешне не связанными падениями дальше по сьюту: два теста всё
ещё проверяли `pool !== null` (старый nullable-контракт) вместо `pool.length === 0`, и один из них
падал на этом устаревшем assert **до** того, как достигал собственной задокументированной защиты
от межтестового загрязнения (специально добавленное ожидание слива намеренно-медленного мокового
ответа внутри того же теста, который его зарегистрировал) — ранний throw пропускал этот слив, а
это ровно тот баг "следующий тест ловит случайный лишний вызов", от которого эта защита и должна
спасать. Починка устаревшего assert-а починила оба падения разом — не два отдельных бага, одна
общая причина.

## Немедленный ретрай на уровне трекера

Прямой запрос тем же днём, следом за переделкой на параллельный поиск: "Если ошибка отвала по
таймауту, то задержку повтора не использовать. По каждому трекеру ретраить до исчерпания попыток
если идут ошибки." Три отдельных требования, закрыты вместе:

- **`SearchOneIndexerAsync` ретраит один упавший индексатор НЕМЕДЛЕННО** (без задержки), до
  `IndexerMaxAttempts` (3) попыток суммарно, при любой ошибке включая собственный таймаут в 30с —
  разбит на внешний `SearchOneIndexerAsync` (цикл ретраев, отчитывается кумулятивным `ElapsedMs`
  по всем попыткам сразу — честное общее время, потраченное на этот индексатор, а не только время
  последней попытки) и внутренний `SearchOneIndexerAttemptAsync` (исходное тело одного HTTP-вызова,
  без изменений).

  Осознанно **не** переиспользует форму backoff-лестницы `POOL_RETRY_DELAYS_MS` —
  пользователь явно исключил это ("задержку повтора не использовать"), и два механизма ретраев
  решают разные проблемы: лестница пула — для редкого случая "не ответил вообще ни один
  индексатор"; этот — потому что одна ошибка одного индексатора обычное дело и дёшево ретраить
  немедленно, раз параллелизм и так уже гарантирует, что застрявший трекер не блокирует остальных.

  Стоит зафиксировать как реально принятый компромисс, а не недосмотр: раз `SearchJob.Done`
  требует, чтобы отчитался **каждый** индексатор (успехом или финальной ошибкой), прежде чем весь
  пул переключится в `poolStatus:'ready'`, постоянно падающий индексатор теперь может занимать до
  `IndexerMaxAttempts × 30с` (90с в худшем случае) до того, как ОБЩИЙ поиск устаканится — но виджет
  (см. следующий раздел) весь это время показывает именно этот индексатор живым спиннером, а
  результаты/бейджи всех ОСТАЛЬНЫХ индексаторов уже прогрессивно видны независимо от этого (селекторы
  "кандидаты вперёд" вообще не ждут `poolStatus`) — так что эта цена полностью видна пользователю,
  а не превращается в тихое зависание.

## Именованный виджет ожидаемых трекеров

- **`/api/torrent-search/start` вернул `indexers: [{id, name}]`** — полный список
  сконфигурированных индексаторов, известный до того, как хотя бы один результат физически мог
  прийти, поверх уже существующих `jobId`/`totalIndexers`. Именно это делает возможным "спиннер
  по имени" — без этого клиент узнаёт имя индексатора только когда тот уже отчитался (успехом или
  ошибкой), а всё ещё ожидаемый трекер мог бы показываться только анонимным счётчиком.
  `startParallelSearch` получил пятый опциональный колбэк `onIndexerList(list)`, вызывается один
  раз синхронно внутри обработчика ответа `/start`, прокинут через `searchTorrentModProgressive` и
  обе обёртки `searchMovieTorrentsProgressive`/`searchSeriesTorrentsProgressive` вниз до
  `loadAllTorrents`, которая сохраняет это как новое поле `poolAllIndexers` (сбрасывается в `[]`
  вместе с `pool`/`poolIndexers` на каждом свежем поиске).

- **Ранее добавленное поле `poolIndexersTotal` (голый счётчик) убрано целиком** — как только
  известен полный список, отдельно поддерживаемый счётчик становится вторым источником истины для
  того же факта без причины существовать; `total` теперь это просто `poolAllIndexers.length`.

- **`selectPoolIndexers` переписан так, чтобы возвращать по одной записи на КАЖДЫЙ
  сконфигурированный индексатор**, не только на уже ответившие — сравнивает
  `state.poolAllIndexers` со `state.poolIndexers`, выдавая `{id, name, status:
  'pending'|'ok'|'error', error, elapsedMs}` на трекер. `renderTrackers` рисует
  `torrent-mod__spinner` на каждой записи `'pending'`, по имени — это буквально ответ на запрос
  "показывать со спиннером кого ещё ждём", раньше это был только агрегатный счётчик "ждём ещё N".

- **Успешно ответившие трекеры сначала прятались по таймауту** (`TRACKER_SUCCESS_HIDE_MS`,
  4000 мс) — прямой ответ на "успешные скрывать по таймауту": как только несколько трекеров уже
  отчитались, растущая стена зелёных "ok"-чипов становится ровно тем шумом, ради устранения
  которого виджет и придуман; упавший или всё ещё ожидаемый трекер держит свой чип бессрочно —
  именно они требуют внимания.

Этот первоначальный вариант реализации fade-таймаута оказался **неправильным по слою** — см.
следующий раздел, это самая ценная часть документа.

## История: где на самом деле проходит граница View и Domain

Это отдельная, самая поучительная часть переделки — стоит прочитать целиком, а не только вывод.

### Симптом

После того как все чипы трекеров исчезли, место, которое они занимали, оставалось зарезервированным
— пользователь сообщил напрямую: "после исчезания всех трекеров надо место вверху освободить, а то
пустота там остаётся". Причины оказались две, независимые:

1. `.torrent-mod__trackers` держал свой нижний padding в `1em` безусловно, даже с нулём детей — CSS
   не схлопывает padding пустого блока просто потому, что он пуст. Исправлено
   `.torrent-mod__trackers:empty{padding:0}`.
2. `renderTrackers` делал ранний `return`, как только `progress.trackers.length` было 0, что
   пропускало собственный вызов `Lampa.Layer.update()` именно в этом случае. Исправлено переносом
   вызова так, чтобы он выполнялся безусловно, после `forEach`.

Оба этих фикса были правильными сами по себе — но фикс исходного механизма "спрятать чип по
таймауту", на котором они держались, прошёл через **две** последовательные коррекции архитектуры
от пользователя в тот же день, прежде чем добрался до правильного дизайна. Обе коррекции
заостряют один и тот же принцип, который эта кодовая база уже декларирует, но именно на этой фиче
он ещё не был проверен на практике.

### Раунд 1: рендер в логике вместо наблюдения

Первая реализация fade-по-таймауту была тикающим `setInterval`, который звал `renderTrackers`
**напрямую**, в обход store — потому что в `state.poolIndexers` буквально ничего не меняется, когда
проходит 4 секунды, меняется только `Date.now()`.

Пользователь поймал это немедленно и точно: *"Разве эта разметка не должна на изменение стейта
отрабатывать всё? Мы же для этого его и делали. Опять где-то рендер в логике у тебя, вместо
наблюдения?"* — это ровно тот сбой "рендер в логике вместо наблюдения", ради предотвращения
которого и существует всё разделение Store/реактивный View.

**Первая попытка исправить** это выглядела правильно на первый взгляд: перенести само
**планирование** таймера в domain-слой (`episodes-interactor.js` заводит `scope.setTimeout`,
который со временем сам вызовет `store.patch({poolIndexers: pool.slice()})`, позволяя уже
существующему реактивному diff-and-render подхватить изменение естественным образом). Это
формально устраняло претензию "рендер вне подписки".

### Раунд 2: планирование в domain — тоже неправильный слой

Немедленно следом пользователь поправил и **эту** попытку, более острым тезисом: *"Таймеры
фейдинга должны в рамках вьюмодели работать. Таймер фейда — это UI логика, а не домена. Вот для
этого я и просил разделение. Процесс поиска спокойно наполняет стор, а во вьюмодели создаются
мягкий плавный вид для пользователя. С анимациями появления, исчезновения, сдвигания/раздвигания
списка."*

Это тоже верно, и точнее, чем раунд 1: то, что fade превратили в "настоящий переход состояния" (то
есть провели его через `store.patch`), само по себе не значит, что **domain** должен владеть его
планированием. `TRACKER_SUCCESS_HIDE_MS` (сколько держать успешный чип, прежде чем убрать его из
виду) — это значение presentation/UX-тюнинга, а не факт предметной области; работа domain
заканчивается на фиксации `reportedAt` (когда именно этот индексатор ответил) и не идёт дальше.
Более того, размещение задержки скрытия внутри `episodes-interactor.js` структурно блокировало
именно те плавные анимации (появление/исчезновение/сдвиг списка), которых пользователь и хотел:
единое обновление вида "значение изменилось — перерисовать всё", управляемое `store.patch()`, не
имеет места, за которое можно подвесить CSS-переход конкретного DOM-узла, привязанный к его
собственному жизненному циклу.

### Итоговый, правильный дизайн

- **`selectPoolIndexers` (`domain/results-selectors.js`) отчитывает КАЖДЫЙ сконфигурированный
  индексатор ВСЕГДА**, `{id, name, status, error, elapsedMs, reportedAt}`, без какой-либо
  фильтрации по времени со своей стороны — чистое переформатирование уже сохранённых фактов, без
  какого-либо мнения о длительности видимости.
- **`TRACKER_SUCCESS_HIDE_MS` полностью выехал из `shared/state.js`**, в локальную константу
  внутри `ui/results-screen.js` — у неё теперь ровно один читатель, никакого межфайлового
  соглашения защищать не нужно.
- **`renderTrackers` переписан** из функции "стереть-и-перестроить весь ряд целиком" в настоящий
  per-chip DOM-lifecycle, сверяемый с View-локальной картой `trackerNodes` (`id -> {node,
  hideTimer}` — обычная бухгалтерия View, та же категория, что уже существующие в этом файле
  `episodeRows`/`lastFocusedNode`, не состояние store):
  - чип, новый в `progress.trackers`, вставляется с классом `--enter` (свёрнутое состояние:
    `opacity:0; max-width:0; margin-right:0`), который снимается тиком позже, чтобы у браузера
    было настоящее исходное состояние, из которого можно перейти;
  - чип, переходящий `pending -> ok`/`error`, обновляет класс/текст своего уже существующего узла
    на месте, без анимации входа (он никуда не уходил);
  - каждый раз, когда чип отчитывается `status:'ok'`, `renderTrackers` планирует (через
    `domain.scope.setTimeout` — всё ещё безопасный для утечек, всё ещё тот же общий lifecycle,
    просто теперь на правильном слое) одноразовое скрытие через
    `TRACKER_SUCCESS_HIDE_MS - (Date.now() - reportedAt)`, с защитой от повторного планирования
    при перерисовке до срабатывания. Этот таймер добавляет класс `--leave` (то же свёрнутое
    конечное состояние, что и `--enter` — фактически один общий CSS-класс "не видно" для обоих
    направлений), и, после того как переход в 0.25с успел завершиться, реально `.remove()`-ит узел
    и вызывает `Lampa.Layer.update()`.
- **Отступы между чипами переехали с `gap` контейнера на `margin-right` каждого чипа**
  (styles.js) — именно для того, чтобы этот переход давал эффект "список сдвигается, закрывая
  дыру" ("сдвигания/раздвигания списка"): `gap` не участвует в переходе схлопывающегося элемента
  так, как участвует margin, так что при `gap` осталась бы фиксированная дыра там, где был чип,
  даже пока сам чип визуально схлопывался до нуля.

### Настоящий баг анимации входа, найденный только вживую

Первая версия финального дизайна снимала класс `--enter` через двойной
`requestAnimationFrame` — обычный, в норме правильный приём, чтобы заставить браузер
отрисоваться между добавлением и снятием класса. Подтверждено вживую через
`document.hidden`/`visibilityState`: вкладка Browser pane автоматизационного харнеса в момент
проверки была в фоне, а Chromium **полностью** приостанавливает колбэки
`requestAnimationFrame` для скрытых вкладок — снятие класса ни разу не отработало, из-за чего
затронутые чипы навсегда оставались свёрнутыми (невидимыми) вместо плавного появления.

Это не баг, который бы затронул реальное целевое устройство (приложение на LG WebOS TV всегда
находится на переднем плане, понятия "вкладка в фоне" там не существует), но опора на rAF делала
механизм хрупким к этому классу окружения без всякой реальной выгоды — заменено на
`domain.scope.setTimeout(fn, 0)`, у которого нет зависимости от видимости вкладки вообще, и который
одинаково корректен ("следующий макротаск, не тот же тик") на по-настоящему видимом экране.

**Общий урок для этой кодовой базы**: `requestAnimationFrame` — не безопасный примитив
планирования по умолчанию здесь, даже несмотря на то, что эта сборка Lampa построена на Chromium
— предпочитать `domain.scope.setTimeout`, если только что-то специально не нуждается в точности
привязки к кадру, а в этом плагине сейчас ничего такого нет.

### Общий вывод из обеих коррекций

При исправлении нарушения границы слоёв стоит проверять — переместилась ли забота **на
правильный слой**, или просто переехало **место**, где живёт неправильный по сути код. Раунд 1
исправил букву правила "не рендерить вне подписки", но раунд 2 показал, что этого недостаточно:
значения presentation-тюнинга и тайминг анимации принадлежат View, а не domain, даже если
технически проходят через store.

### Тесты

`domain.test.mjs`'s `selectPoolIndexers`-кейс переписан так, чтобы проверять **противоположное**
тому, что было раньше: давно отчитавшийся успех по-прежнему возвращается, без фильтрации, с
настоящим `reportedAt` — доказывая, что у селектора больше нет собственного мнения о сокрытии.
`smoke.test.mjs` получил кейс, утверждающий, что `state.poolIndexers` **не** получает новую
ссылку сам по себе далеко за пределами старого окна скрытия (domain остаётся инертным, как
только записал факты) — намеренная проверка **отсутствия** механизма, который раунд 1
ошибочно туда добавил, чтобы будущий регресс назад к "domain сам планирует своё скрытие" был
пойман немедленно. Само fade/анимация остаётся вне автоматического покрытия, в рамках уже
установленной для `ui/` границы этого проекта ("проверяется вживую", не юнит-тестами) —
проверено вживую вместо этого: `document.hidden` подтвердил причину rAF-бага, затем подтвердил
фикс (класс `--enter` корректно снимается даже в фоне); полный живой поиск с реально
медленным/ретраящимся трекером (NewStudio, 19.5с через per-indexer ретрай) показал, как каждый
чип анимированно появляется, медленный всё ещё видимо крутится, пока остальные уже исчезли, а
контейнер виджета устаканивается в `{childCount:0, paddingBottom:'0px', height:0}` по завершении
— подтверждая, что исходно репортнутый баг (остающаяся пустота) действительно исправлен целиком,
а не залатан снаружи.

## Реальный баг, переживший весь зелёный тест-сьют

`domain/series-results-viewmodel.js`/`movie-results-viewmodel.js` — оба 22-строчные
проброс-обёртки над `createResultsDomain`, явно перечисляющие, какие поля прокидывать во View,
вместо того чтобы спредить весь domain-объект целиком — новое поле `scope` (появившееся вместе с
lifecycle-переделкой) не попало ни в один из двух списков. Каждый тест этого сьюта строит domain
напрямую через `createResultsDomain`, минуя обе обёртки — поэтому ничего это не поймало. Баг
проявился только на настоящем живом клике по кнопке Torrent Mod: `TypeError: Cannot read
properties of undefined (reading 'subscribe')` внутри вызова `domain.scope.subscribe(...)` в
`ui/results-screen.js`, который собственный try/catch у `Lampa.Component.create` тихо подменил
на generic пустой экран — никакой видимой ошибки на самом экране, только в консоли devtools.

Исправлено добавлением `scope: domain.scope` в оба возвращаемых объекта обёрток; новый
`domain.test.mjs`-кейс строит каждую обёртку напрямую и проверяет, что `.scope.subscribe` —
настоящая функция, закрывая именно ту дыру в покрытии, которая это пропустила (обход слоя
View/DOM целиком, как и любой другой domain-тест, поэтому не пересекает заявленную для `ui/`
границу проекта).

Отдельно, в ходе той же проверки: устаревший файл-переопределение для разработки
`%LocalAppData%\TorrServer\dev-plugins\TorrentModPlugin.js`, оставшийся от `npm run dev:plugin` в
той же сессии, подменял собой только что опубликованный embedded-ресурс (`BuiltInPlugins.Read`
по дизайну сначала проверяет dev-override путь). Не баг кода, просто напоминание: собственный
dev-loop проекта требует явного шага очистки (удалить override либо снова прогнать `npm run
install:plugin-dev`) перед тем, как доверять деплою как "проверенному вживую" — устаревший
dev-override читается точно как настоящий регресс, пока не знаешь, что нужно проверить и это.
