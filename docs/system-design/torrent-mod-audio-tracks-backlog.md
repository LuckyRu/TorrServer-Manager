# Бэклог: выбор аудиодорожки в Torrent Mod

Процессный документ — не ADR (решение о направлении ещё не принято, это отложено осознанно). Здесь
зафиксировано исследование от 2026-08-08: почему субтитры уже переключаются, а аудиодорожки нет,
что нужно поменять и почему это отложено, а не сделано сразу. Источник фактов —
`vendor/lampa-source` (склонирован ранее) и `vendor/torrserver-source` (склонирован для этого
исследования, тоже гитигнорирован, чисто для чтения — см. `.gitignore`).

## Симптом

Пользователь может переключать субтитры в плеере, но не аудиодорожки — при том что в файле их
несколько (проверено на реальном фильме).

## Провал первой попытки (v1.17.23, откачен в v1.17.24)

До этого исследования уже была одна попытка: `Services/PluginHub.cs` проксировал
`/gst/{hash}/master.m3u8`, переписывал его в HLS `#EXT-X-MEDIA:TYPE=AUDIO` вручную (на основе
отдельного `/ffp`-запроса), отдавал плееру. Подвесила и в итоге уронила сам процесс TorrServer —
причина задокументирована в `CLAUDE.md` (коммит `6c54515`): `/gst/.../master.m3u8` сам по себе
занимает ~20с (прогрев GStreamer pipeline), а прокси делал этот запрос ПОСЛЕДОВАТЕЛЬНО перед ещё
одним (`/ffp`), упираясь в общий `httpClient.Timeout=25с`; повторные запросы (свои и от плеера)
сталкивались с и так нестабильным управлением pipeline на стороне TorrServer. Урок не «идея плохая»,
а «сделано небрежно, без учёта реальной стоимости прогрева pipeline» — этот документ существует,
чтобы вторая попытка (если будет) не повторила ту же небрежность.

## Почему субтитры работают, а звук — нет (подтверждено вживую)

Голый (без нашего участия) ответ `GET /gst/{hash}/{fileID}/master.m3u8?index=N&audio=0` от
TorrServer уже содержит несколько `#EXT-X-MEDIA:TYPE=SUBTITLES` записей (на реальном фильме — 6
дорожек, разные языки) — TorrServer формирует это сам, без единого лишнего запроса с нашей стороны.
Но `#EXT-X-MEDIA:TYPE=AUDIO` в этом же ответе нет вообще — единственный `#EXT-X-STREAM-INF`
вариант ссылается на `video.m3u8?audio=0`, то есть звуковая дорожка выбирается ПАРАМЕТРОМ запроса,
а не перечисляется как альтернатива.

## Как это устроено в исходнике TorrServer (`server/gstreamer/`)

Прочитано напрямую (`vendor/torrserver-source/server/gstreamer/handlers.go`,
`service.go`), не угадано:

- **`buildVariantPlaylist`** (`handlers.go`) — та самая функция, что строит master-плейлист. Цикл
  по субтитрам (`for _, track := range task.Probe.Tracks`, фильтр `supportedSubtitleTrack`,
  условие `task.Config.Subtitles`) пишет одну `#EXT-X-MEDIA:TYPE=SUBTITLES` запись на трек.
  Аналогичного цикла для аудио **нет вообще** — только один вариант с `audio` из query-параметра,
  вшитым в `video.m3u8?audio=N`.
- **Данные уже есть.** `task.Probe.Tracks` — то же самое поле, из которого строится список
  субтитров — содержит и аудиодорожки (индекс, язык, название), просто код их не перебирает.
  Значит недостающая часть — не данные, а код: нужен цикл-аналог субтитрового, плюс
  `AUDIO="audio"` в `#EXT-X-STREAM-INF` (условно, как уже сделано для `SUBTITLES="subs"`).
- **Настоящее препятствие — не в manifest-е, а в кэшировании задач.** `GetOrAdd(hash, fileID,
  audio)`/`getOrAdd` (`service.go`) кэширует `*Task` (GStreamer pipeline) по ключу, включающему
  `audio` (`task.Audio == audio` — прямое условие попадания в кэш). Значит **каждая аудиодорожка
  — отдельный pipeline**, не переключение внутри уже работающего. Даже добавив цикл выше,
  переключение дорожки означало бы полный холодный старт нового pipeline — те же ~20с+, что мы
  только что боролись подружить с таймаутом hls.js, но теперь на КАЖДОЕ переключение, а не один раз
  на старте. Реальная бесшовная смена дорожки потребовала бы более глубокого изменения — один
  pipeline, мультиплексирующий все аудиодорожки разом, отдающий их как параллельные HLS-рендишены
  одного видеопотока. Код самого построения pipeline (где заводятся GStreamer-элементы) **ещё не
  прочитан** — не могу пока оценить сложность этой части.

## Рассмотренный путь: сабмодуль + патчи поверх апстрима

Технически рабочий план (git submodule, запиненный на тег + версионированные `.patch`-файлы,
применяемые перед `go build`; апдейт — `git submodule update --remote` + переприменение патчей).
Цена, которую стоит явно взвесить перед тем как за это браться:

1. **Go-тулчейн становится обязательной зависимостью сборки.** Сейчас — намеренно только .NET SDK
   + Node.js (см. `CLAUDE.md`). GStreamer dev-заголовки тоже потребуются для сборки TorrServer.
2. **Патчи требуют постоянного сопровождения**, не разового — каждый новый релиз апстрима может
   сломать применение патча, особенно раз он трогает именно тот код, который апстрим вероятнее
   всего продолжит менять.
3. **Смена модели доверия дистрибуции**: сейчас `Services/UpdateService.cs` скачивает официальный
   релиз YouROK и сверяет ИХ checksum. С патченной сборкой мы сами собираем и подписываем свой
   бинарник — берём на себя supply-chain ответственность, которую раньше нёс апстрим. Это
   отдельный, не тривиальный редизайн `UpdateService.cs`.
4. **Патч на manifest один не решает проблему** — см. препятствие выше: без изменения pipeline
   переключение дорожки всё равно будет холодным стартом на ~20с+.

## Что нужно сделать, чтобы разморозить это решение

- Прочитать код построения GStreamer pipeline в `vendor/torrserver-source/server/gstreamer/`
  (не `handlers.go`/`service.go` — сам pipeline, вероятно `task.go` или соседний файл) и оценить,
  насколько тяжело сделать один pipeline с несколькими аудио-выходами вместо одного pipeline на
  дорожку.
- Явно решить: устраивает ли «холодная» смена дорожки (~20с на клик) как временный компромисс, или
  ждать полноценного мультиплексирования — это меняет объём патча на порядок.
- Если решение — патчить апстрим: завести реальный (не гитигнорированный) git submodule и
  спроектировать, как `UpdateService.cs` будет собирать/распространять патченный бинарник.
