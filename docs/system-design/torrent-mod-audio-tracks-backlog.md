# Бэклог: выбор аудиодорожки в Torrent Mod

Процессный документ — не ADR (решение о направлении ещё не принято, это отложено осознанно). Здесь
зафиксировано исследование от 2026-08-08: почему субтитры уже переключаются, а аудиодорожки нет,
что нужно поменять и почему это отложено, а не сделано сразу. Источник фактов —
`vendor/lampa-source` (склонирован ранее) и `external/TorrServer` (закреплённый git submodule).

## Симптом

Пользователь может переключать субтитры в плеере, но не аудиодорожки — при том что в файле их
несколько (проверено на реальном фильме).

## Провал первой попытки (v1.17.23, откачен в v1.17.24)

До этого исследования уже была одна попытка: `Services/PluginHub.cs` проксировал
`/gst/{hash}/master.m3u8`, переписывал его в HLS `#EXT-X-MEDIA:TYPE=AUDIO` вручную (на основе
отдельного `/ffp`-запроса), отдавал плееру. Подвесила и в итоге уронила сам процесс TorrServer —
причина задокументирована в `CLAUDE.md` (коммит `6c54515`): `/gst/.../master.m3u8` сам по себе
занимал ~20с. Позднее уточнение: исходник подтверждает, что смена task не вызывает `DropTorrent`,
но не позволяет разложить эти ~20с между доступностью кусочков из torrent и созданием GStreamer
pipeline — это требует live trace. Прокси делал этот запрос ПОСЛЕДОВАТЕЛЬНО перед
ещё одним (`/ffp`), упираясь в общий `httpClient.Timeout=25с` — рассчитанный под другие, быстрые
proxy-вызовы в этом же файле, а не под ~20-секундный ответ GST-манифеста. Даже когда суммарное время
укладывалось в этот таймаут, добавленной задержки хватало, чтобы собственный HLS-клиент плеера сам
обрывал запрос и повторял его. Повторные запросы (свои и от плеера) сталкивались с и так нестабильным
управлением pipeline на стороне TorrServer — в `server.log` уже тогда встречались
`gstreamer state change timed out`, `master init failed: segment is not ready` и `seek ... while
reusing pipeline`, причём для раздач, вообще не касавшихся нового кода. Откатили, а не залатали
таймаутом: более длинный `httpClient.Timeout` не устранил бы саму нестабильность переиспользования
pipeline на стороне TorrServer, а лишь спрятал бы симптом. Урок не «идея плохая»,
а «нельзя добавлять последовательные тяжёлые запросы, пока не измерены доступность данных и pipeline»
— этот документ существует, чтобы вторая попытка этого не повторила.

## Почему субтитры работают, а звук — нет (подтверждено вживую)

Голый (без нашего участия) ответ `GET /gst/{hash}/{fileID}/master.m3u8?index=N&audio=0` от
TorrServer уже содержит несколько `#EXT-X-MEDIA:TYPE=SUBTITLES` записей (на реальном фильме — 6
дорожек, разные языки) — TorrServer формирует это сам, без единого лишнего запроса с нашей стороны.
Но `#EXT-X-MEDIA:TYPE=AUDIO` в этом же ответе нет вообще — единственный `#EXT-X-STREAM-INF`
вариант ссылается на `video.m3u8?audio=0`, то есть звуковая дорожка выбирается ПАРАМЕТРОМ запроса,
а не перечисляется как альтернатива.

## Как это устроено в исходнике TorrServer (`server/gstreamer/`)

Прочитано напрямую (`external/TorrServer/server/gstreamer/handlers.go`,
`service.go`), не угадано:

- **`buildVariantPlaylist`** (`handlers.go`) — та самая функция, что строит master-плейлист. Цикл
  по субтитрам (`for _, track := range task.Probe.Tracks`, фильтр `supportedSubtitleTrack`,
  условие `task.Config.Subtitles`) пишет одну `#EXT-X-MEDIA:TYPE=SUBTITLES` запись на трек.
  Аналогичного цикла для аудио **нет вообще** — только один вариант с `audio` из query-параметра,
  вшитым в `video.m3u8?audio=N`.
- **Данные уже есть.** `task.Probe.Tracks` — то же самое поле, из которого строится список
  субтитров — содержит и аудиодорожки (индекс, язык, название), просто код их не перебирает.
  Значит недостающая часть — не данные, а код: нужен цикл-аналог субтитрового, плюс
  `AUDIO="audio"` в `#EXT-X-STREAM-INF` (условно, как уже сделано для `SUBTITLES="subs"`).
- **Настоящее препятствие — не в manifest-е, а в жизненном цикле задач.** `GetOrAdd(hash, fileID,
  audio)`/`getOrAdd` (`service.go`) хранит `*Task` (GStreamer pipeline) в map **только по `hash`**.
  `task.Audio == audio` — это условие переиспользования, но не часть ключа: запрос для другого
  `audio` создаёт новую задачу, записывает её под тем же hash и dispose-ит предыдущую. Поэтому
  несколько URL `audio=N` в одном HLS manifest-е ещё опаснее, чем казалось первоначально: их
  параллельная загрузка будет взаимно останавливать pipelines. `pipeline_gst.go` подтверждает,
  что в задаче собирается один audio branch в `mux.audio_0`, а не несколько HLS audio renditions.
  Реальная бесшовная смена потребует одного pipeline с несколькими раздельными audio outputs.

## Рассмотренный путь: downstream-форк как субмодуль

Решение реализовано: `external/TorrServer` подключён как git submodule на форк
`LuckyRu/TorrServer`, а расширения GST находятся в ветке `torrserver-manager` отдельными
коммитами. Точный собираемый commit фиксируется gitlink родительского репозитория; lock-файл и
локальные `.patch`-файлы не нужны. Рабочее дерево субмодуля не изменяется сборкой.

Оставшиеся эксплуатационные издержки:

1. **Go-тулчейн становится обязательной зависимостью сборки.** Сейчас — намеренно только .NET SDK
   + Node.js (см. `CLAUDE.md`). GStreamer dev-заголовки тоже потребуются для сборки TorrServer.
2. **Downstream-коммиты требуют постоянного сопровождения**, не разового — каждый новый релиз
   апстрима может потребовать rebase или ручного разрешения конфликтов, особенно раз изменения
   трогают код, который апстрим вероятнее всего продолжит менять.
3. **Смена модели доверия дистрибуции**: `Services/UpdateService.cs` продолжает отслеживать
   официальные релизы YouROK, а сборщик подтверждает официальный базовый тег и собирает pinned commit
   форка. Мы сами собираем свой бинарник, поэтому provenance остаётся виден в истории форка,
   gitlink и выводе сборки.
4. **Патч на manifest один не решает проблему** — см. препятствие выше: без изменения pipeline
   переключение дорожки пересоздаст GST-задачу. При этом код не вызывает `DropTorrent`, поэтому
   переключение не делает намеренный сброс cache того же hash; наличие нужных кусков и видимую
   задержку нужно подтвердить live-тестом.

## Что осталось сделать для дальнейшего развития

Исследование pipeline завершено. Для выбранного временного решения см.
[системный дизайн MVP](torrent-mod-audio-track-mvp.md): оно использует один контролируемый
GST-перезапуск по `audio=N`, не добавляет несколько URL в manifest и не требует патча апстрима.
Полноценный вариант с HLS audio renditions остаётся отдельным будущим проектом.
