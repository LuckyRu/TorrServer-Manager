## Правила, общие для всех этапов

- **Один этап — один или два коммита**, каждый оставляет систему рабочей: `go test -tags=gst
  ./gstreamer` зелёный, `scripts\build-all.ps1` проходит целиком.
- **Инварианты И1–И3** из [`gstreamer-pipeline-robustness.md`](gstreamer-pipeline-robustness.md)
  сохраняются на каждом шаге. Э2 трогает `Task` и `service.go` — те самые места, где их легко
  сломать; при конфликте перечитать §1 того документа, а не полагаться на тесты.
- **Откат** — `git revert` одного коммита в форке плюс обновление gitlink. Поэтому этапы нельзя
  схлопывать в один коммит.
- **Прогон под `-race`** после каждого этапа (WSL, см. §7). Модель идентичности целиком про
  разделяемое состояние.

## Э1. Идентичность клиента, без смены поведения

Цель — научиться *различать* клиентов и видеть их в логах, ничего пока не меняя в маршрутизации
задач. Самостоятельная ценность: сегодня на вопрос «кто именно устроил шторм» ответа нет.

**Новый файл `gstreamer/client.go`:**

```go
// clientID возвращает устойчивую идентичность клиента.
//
// Явный идентификатор устройства — единственный надёжный источник: он переживает смену адреса и
// различает два приложения на одном устройстве. Отпечаток по адресу и агенту — запасной вариант
// для клиентов, которые ничего не присылают; в домашней сети этого достаточно.
func clientID(c *gin.Context) string {
    if explicit := strings.TrimSpace(c.Query("client")); explicit != "" {
        return "c:" + shortSum(explicit)
    }
    host, _, err := net.SplitHostPort(c.Request.RemoteAddr)
    if err != nil {
        host = c.Request.RemoteAddr
    }
    return "d:" + shortSum(host + "\x00" + c.Request.UserAgent())
}

// sessionToken детерминирован: плеер перезапрашивает master.m3u8 при ошибках, и случайный токен
// плодил бы новый пайплайн на каждую перезагрузку плейлиста.
func sessionToken(client string, hash string, fileID string, audio int) string {
    return shortSum(client + "\x00" + hash + "\x00" + fileID + "\x00" + strconv.Itoa(audio))
}

func shortSum(value string) string {
    sum := sha256.Sum256([]byte(value))
    return hex.EncodeToString(sum[:8])
}
```

**`gstreamer/log.go`** — добавить клиента в контекст сообщений об ошибках рядом с `hash`/`file`.
После этого строка вида `hash=… file=3 client=d:1a2b… segment 3 response failed` сразу отвечает,
чей это шторм.

**Наблюдаемость деградации.** Идентичность — контракт оптимизации, а не предусловие: клиент без
явного `client` обязан работать, просто хуже. Значит эта «хуже» должна быть видна, иначе «две
вкладки мешают друг другу» будет выглядеть загадочным багом воспроизведения. Логировать:

- что клиент работает на производном отпечатке, а не на явном идентификаторе (один раз на сессию,
  не на каждый запрос);
- когда два независимых потока схлопнулись в один отпечаток — это и есть момент, когда изоляция
  молча выключилась.

**Проверить:** `go test`, и что `shortSum` устойчив (тот же вход → тот же токен).

**Риск:** низкий, поведение не меняется.

**Сделано иначе.** В токен добавлен `hash`: `fileID` — это индекс файла внутри раздачи, поэтому без
хэша файл 3 двух разных раздач дал бы один ключ карты задач. Проверка `task.Hash == hash` при
резолве не помогает — коллизия происходит раньше, при вставке.

`Task` получил `ClientID` уже на этом этапе (а не на Э2), чтобы `gstTaskLogPrefix` называл клиента
во всех логах пайплайна сразу — иначе ценность этапа сводилась бы к двум строкам в обработчиках.

## Э2. Ключ задачи — токен сессии

Ядро работы. Задача перестаёт быть «слотом торрента» и становится «сессией клиента на файле».

### 2.1. Маршруты

В `SetupRoute` ([handlers.go:20](../../external/TorrServer/server/gstreamer/handlers.go)) добавить
зеркальный набор с сегментом сессии:

```go
route.GET("/gst/:hash/c/:token/video.m3u8", s.videoPlaylist)
route.GET("/gst/:hash/c/:token/init.mp4",   s.initMP4)
route.GET("/gst/:hash/c/:token/seg/*segment", s.segment)
route.GET("/gst/:hash/c/:token/subs/*subtitle", s.subtitle)
```

`master.m3u8`, `probe`, `heartbeat` остаются на прежних путях: первый минтит сессию, второй
торрент-уровневый по смыслу, третий тоже (см. 2.5).

⚠️ Gin падает на конфликте маршрутов при старте, а не в рантайме. Зарегистрировать и **запустить**
сервер — это и есть проверка.

### 2.2. Генерация плейлистов

В `buildVariantPlaylist` два абсолютных URL — `video.m3u8`
([handlers.go:205](../../external/TorrServer/server/gstreamer/handlers.go)) и `subs/*.m3u8`
([handlers.go:135](../../external/TorrServer/server/gstreamer/handlers.go)) — получают префикс
`/gst/<hash>/c/<token>`.

`init.mp4` ([handlers.go:291](../../external/TorrServer/server/gstreamer/handlers.go)) и `seg/N.m4s`
([handlers.go:312](../../external/TorrServer/server/gstreamer/handlers.go)) — **относительные, их не
трогать**: они разрешаются относительно `video.m3u8` и подхватят токен сами. То же для
`buildSubtitlePlaylist`, который переписывает строки `seg/` в `<track>/<index>.vtt`.

### 2.3. Ключ карты задач

```go
tasks map[string]*Task   // service.go:44 — ключ становится token, а не hash
```

`Task` получает поля `ClientID`, `Token`, `Hash` (последнее — потому что хэш перестаёт быть ключом,
но нужен торрент-слою и логам).

Переписать на токен: `Get` → `GetSession` ([service.go:747]), `TryRemove`, `detachTask`,
`tryRemoveExpectedInactive`, `isCurrentTask`, `cleanupInactive`, `evictTasksForLimitLocked`,
`oldestEvictableTask`. Структурно они не меняются — меняется смысл ключа.

`GetOrAdd` получает `clientID` и внутри вычисляет токен; `id := hash` ([service.go:172]) уходит.

### 2.4. Что удалить

Механизмы против борьбы за слот теряют предмет — бороться больше не за что:

- `swapDefended` и `taskSwapGrace` ([service.go:240]);
- цикл попыток с `taskSwapAttempts`/`taskSwapBackoff` и возвратом `ErrTaskBusy` из `GetOrAdd`;
- ключ singleflight по тройке — тройка теперь и есть ключ задачи, достаточно токена.

Удалять, а не оставлять «на всякий случай»: они маскируют поведение новой модели. Вместе с ними
уходит часть тестов из 0008 — те, что про `swapDefended` и вытеснение; тесты кэша cue остаются.

**Сохранить:** `acquireTorrent`/`acquireTorrentWithin` из 0011 — они про И-Т, а не про И-П, и
остаются нужны. Дебоунс сегментов из 0012 тоже остаётся, теперь он естественно ограничен одним
клиентом.

`ErrTaskBusy` перестаёт использоваться здесь, но имя понадобится в Э3 в другом смысле — лучше завести
там отдельную ошибку, чем переиспользовать эту.

### 2.5. Совместимость со старыми путями

Старые URL без `/c/<token>/` приходят только из плейлистов, сгенерированных **прежним процессом**;
после перезапуска сервера задач всё равно нет. Поэтому:

- маршруты без токена оставить зарегистрированными;
- резолвить их как «единственная сессия для этого хэша, если она ровно одна, иначе 404».

Для дома с одним активным клиентом это работает прозрачно, а 404 заставит плеер перезапросить
`master.m3u8` и получить корректные ссылки. Городить таблицу соответствий не нужно.

`heartbeat` сегодня отвечает 404, если `s.Get(hash) == nil`
([handlers.go:49](../../external/TorrServer/server/gstreamer/handlers.go)), — то есть использует
существование задачи как признак «это играют». Заменить на «есть хотя бы одна сессия для этого
хэша». Плагин опрашивает его каждые 2.5 с ради скорости закачки
([smart-preload.js:711](../../Plugins/TorrentModPlugin/playback/smart-preload.js)), менять плагин не
требуется.

### 2.6. `MaxTasks`

Сегодня по умолчанию `0` = без лимита. При задаче на хэш это было терпимо; при задаче на клиента и
файл — уже нет: пять клиентов, переключающих серии, за минуту наплодят десяток пайплайнов. Поставить
осмысленный дефолт (порядка 6 = пять клиентов плюс запас) и отдавать `503` сверх него.

Это изменение наблюдаемого поведения по умолчанию — вынести отдельным коммитом, чтобы откатывалось
независимо.

**Сделано иначе.** «`503` сверх лимита» оказалось слишком грубым: существующее вытеснение по
`LastActive` при задаче-на-сессию делает ровно то, что нужно в обычном случае — выкидывает
брошенную сессию от переключения серий, а не живого зрителя. Поэтому `503` отдаётся только тогда,
когда выкидывать нечего: все занятые слоты обслуживались в последние `sessionActiveGrace` (15 с).
Отказ — это ретрай у плеера; вытеснение живой сессии — остановившаяся картинка у зрителя.

Ошибка своя (`ErrTooManySessions`), а не переиспользованный `ErrTaskBusy`: `ErrTaskBusy` вместе со
всей борьбой за слот удалён на Э2, как и планировалось.

**Проверить:** два клиента на одной раздаче с разными файлами получают разные токены и играют
одновременно; тот же клиент, повторный `master.m3u8` — токен и задача те же.

**Риск:** средний. Меняется схема URL и модель жизненного цикла задач.

## Э3. Лимит читателей на торрент

Уровень И-Т, независим от Э1–Э2 и может делаться параллельно.

Место — `torrstor.Cache.NewReader`
([cache.go:341](../../external/TorrServer/server/torr/storage/torrstor/cache.go)), **не в
gstreamer**: через `/stream` ходят DLNA, WebDAV, прямое скачивание и предзагрузка, и требование
«сервер справляется сам» относится ко всем ним.

```go
func (c *Cache) NewReader(file *torrent.File) *Reader {
    if c.Readers() >= maxReadersPerTorrent {
        return nil
    }
    return newReader(file, c)
}
```

`nil` — уже поддержанный путь отказа: `torr.Torrent.NewReader`
([torrent.go:261](../../external/TorrServer/server/torr/torrent.go)) возвращает `nil` для закрытого
торрента, а `stream.go` это проверяет
([stream.go:85](../../external/TorrServer/server/torr/stream.go)). Ничего изобретать не нужно.

Чтобы отличить «лимит» от «торрент закрыт» и вернуть `503` + `Retry-After` вместо общей ошибки —
завести сентинельную ошибку и поднять её до HTTP-слоя. Отказ, а не очередь: очередь удерживает
HTTP-соединения и лишь переносит проблему.

**Проверить:** клиент открывает больше лимита параллельных range-запросов — сверх лимита `503`,
остальные клиенты не деградируют.

**Риск:** средний — путь затрагивает все виды раздачи, не только GST. Лимит выбрать с запасом
(8–10), чтобы не задеть легитимные сценарии вроде DLNA-обзора.

**Сделано иначе.** Лимит — 12, а не 8–10: постоянный читатель пайплайна на сессию плюс временные
(probe, cue) уже дают до 7 при шести сессиях на одной раздаче, и запас нужен больше, чем строгость.
Предзагрузка в счёт не идёт — `torr/preload.go` открывает `file.NewReader()` напрямую, минуя кэш, и
в `c.readers` не попадает.

Проверка счётчика вынесена в `Cache.admitReader` и делается **под тем же локом**, что и публикация
читателя: раздельные `Readers()` + вставка позволили бы всем одновременным вызовам пройти проверку по
одному и тому же устаревшему счётчику. Это покрыто конкурентным тестом.

`NewReader` теперь возвращает `(*Reader, error)` вместо голого `nil` — иначе «лимит» и «торрент
закрыт» неразличимы, а именно на этом различии стоит выбор между `503` и общей ошибкой.

## Э4. Масштаб ёмкости и пол бюджета

Делать последним: эффект измеряется только под реальной многоклиентской нагрузкой, а до Э2 её не
воспроизвести.

### 4.1. Ёмкость кэша

```
capacity = CacheSize × clamp(активных читателей, 1, N) , с потолком по памяти
```

Пересчитывать при появлении и уходе читателя. Смысл — не «дать про запас», а сохранить условие
работоспособности вытеснения: `cleanPieces` освобождает только куски вне диапазонов читателей, и
если объединение диапазонов перерастает ёмкость, освобождать становится нечего.

**Сделано иначе, и обоснование выше оказалось неверным.** Вытеснение не голодает: `getOffsetRange`
уже делит окно на число активных читателей (`(capacity/readers)`), поэтому объединение диапазонов
при любом их количестве остаётся порядка `capacity`, и освобождать всегда есть что.

Настоящая проблема — обратная сторона того же деления: **окно каждого зрителя сжимается с приходом
следующего**. 64 МБ на пятерых — по 12.8 МБ, что при 4K-битрейте около двух секунд видео. Ёмкость
масштабируется именно поэтому: чтобы после деления на число зрителей каждому осталось окно, которое
он имел бы в одиночку.

Пересчёта по событиям нет — `effectiveCapacity()` считается по запросу. Активность читателя меняется
не только при открытии и закрытии (`readerOn`/`readerOff` в `checkReader`), поэтому события не
покрыли бы все переходы, а вычисление стоит одного `RLock` и умножения.

Потолки: множитель ≤ 4 и ≤ 512 МБ абсолютных, но **никогда не ниже настроенного размера** — если кто-
то сознательно поставил кэш больше потолка, урезать его молча нельзя.

⚠️ **`c.capacity` — обычное поле `int64`**, которое уже пишется без синхронизации в `AdjustRA` и
читается в `cleanPieces`/`GetState`. Это существующая гонка; добавление второго писателя её
усугубит. В этом же коммите перевести на `atomic.Int64` — иначе `-race` справедливо ругнётся, и
будет непонятно, чей это дефект.

### 4.2. Пол бюджета соединений

```go
// cache.go:295
count := max(minConnectionsPerReader, settings.BTsets.ConnectionsLimit / len(readers))
```

Пять соединений на живого зрителя — это голодание. Пол (8–10) гарантирует, что появление фонового
читателя не роняет воспроизведение. Суммарно бюджет может превысить `ConnectionsLimit` — так и
задумано; `EstablishedConnsPerTorrent`
([btserver.go:121](../../external/TorrServer/server/torr/btserver.go)) задаётся один раз при старте,
и в многоклиентском доме его следует поднимать настройкой.

**Проверить:** пять клиентов на одной раздаче — фактическая скорость на каждом и заполнение кэша.

**Риск:** средний — растёт потребление памяти. Потолок обязателен.

**Сделано иначе (4.2).** Заодно исправлен делитель: он считал **всех** читателей, включая
неактивных, хотя цикл раздачи приоритетов их пропускает. Забытый фоном читатель тихо отбирал долю
бюджета у того, кого реально смотрят. Теперь делится на активных.

Пол — 8. При `ConnectionsLimit = 25` это значит: 1 зритель — 25, двое — по 12, пятеро — по 8 (в
сумме 40 > 25, и это намеренно, см. про `EstablishedConnsPerTorrent` выше).

## Э5. Плагин: идентификатор устройства

**Делать вместе с Э2, а не «когда будет время».** Без него модель формально работает, но ровно в
двух местах ведёт себя так, будто её не внедряли:

- две вкладки или два приложения на одном устройстве дают одинаковый отпечаток → общий пайплайн →
  взаимные помехи;
- смена адреса (DHCP, Wi-Fi → Ethernet) меняет отпечаток → новый пайплайн, старый висит до
  таймаута.

При этом этап остаётся **неблокирующим**: сервер обязан обслуживать клиента без `client`, просто
через отпечаток. Никакой «принудиловки» — отсутствие идентификатора не должно быть отказом (разбор
почему — в §4 системного дизайна).

В `smart-preload.js` — генерация UUID один раз на устройство с хранением в `localStorage` и
добавление `&client=<id>` к URL `master.m3u8`
([smart-preload.js:180](../../Plugins/TorrentModPlugin/playback/smart-preload.js)). Больше плагин
никаких URL не строит — остальные приходят из плейлистов, поэтому других изменений в нём не
потребуется.

**Проверить:** две вкладки на одном ПК с одним файлом получают разные токены и не мешают друг другу;
смена IP устройства не создаёт второй пайплайн.

**Риск:** низкий.

**Сделано иначе — и это была ошибка плана, а не мелочь.** UUID из одного `localStorage` **не
закрывает первый случай**: `localStorage` общий для всех вкладок одного origin, поэтому обе вкладки
получили бы один и тот же явный `client` и слились бы в один пайплайн ровно так же, как сливались на
отпечатке.

Идентификатор поэтому состоит из двух половин, `client = <device>.<consumer>`
([client-identity.js](../../Plugins/TorrentModPlugin/playback/client-identity.js)): постоянная в
`Lampa.Storage` (переживает перезапуск и смену адреса — второй случай) и `sessionStorage`, приватная
для вкладки и переживающая перезагрузку страницы (первый случай). Разбор размена — в §4 системного
дизайна.

## Порядок и зависимости

```
Э1 (идентичность) ──> Э2 (ключ задачи) ──┬──> Э5 (плагин, вместе с Э2)
                                          └──> Э4 (ёмкость и бюджет)
Э3 (лимит читателей) — независим, можно в любой момент
```

Э5 стоит парой с Э2, а не в хвосте: без явного идентификатора устройства две вкладки на одном ПК
остаются с общим пайплайном, то есть главный эффект Э2 в этом случае не проявляется.

Минимально полезный срез — **Э1 + Э3**: наблюдаемость плюс защита от лавины соединений, без смены
схемы URL. Если работа прервётся, остановиться лучше здесь.

## Проверка

Юнит-тестами модель не закрывается: она про одновременность и реальные данные. По этапам:

| Этап | Юнит | Живой прогон |
|---|---|---|
| Э1 | детерминированность токена, разбор `client`/отпечатка, лог о работе на отпечатке | — |
| Э2 | резолв сессии, изоляция задач, повторный master не плодит задачу | два клиента, разные файлы одной раздачи; смена серии |
| Э3 | отказ сверх лимита, освобождение при закрытии | 50 параллельных запросов от одного клиента |
| Э4 | пересчёт ёмкости, пол бюджета | пять клиентов, замер скорости и заполнения |
| Э5 | — | две вкладки на одном ПК не мешают друг другу; смена IP не плодит второй пайплайн |

`-race` в WSL после каждого этапа:

```bash
wsl -e bash -lc 'cd /mnt/d/prg/TorrServerManager/external/TorrServer/server && CGO_ENABLED=1 go test -tags gst -race -count=1 ./gstreamer'
```

Живые сценарии — через [`verify-lampa-live`](../how-to/verify-lampa-behavior-live.md) и серверный
лог; для числа одновременных читателей включить `EnableDebug` у TorrServer, тогда в лог пойдут
строки `Connect client (Active streams: N)`.

## Что остаётся нерешённым

- **Дедлайн записи 30 с** из 0003 всё ещё не проверен на медленном клиенте — план его не трогает, но
  под многоклиентской нагрузкой он станет заметнее.
- **Swagger `docs.go`** описывает старые маршруты; после Э2 разъедется с реальностью. Косметика, но
  стоит поправить в том же коммите.
- **Общий пайплайн для клиентов на одном файле** сознательно не делается — см. §9 системного
  дизайна.
