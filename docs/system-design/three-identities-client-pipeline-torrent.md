# Три идентичности: клиент, пайплайн, торрент

Что менять в коде TorrServer, чтобы тракт `клиент → HTTP → GST-пайплайн → торрент` был устойчив к
нескольким одновременным и плохо ведущим себя клиентам.

Область — форк [`LuckyRu/TorrServer`](https://github.com/LuckyRu/TorrServer), ветка
`torrserver-manager`, подключённая как `external/TorrServer`. Документ описывает целевое состояние и
причины; порядок правок — в §7.

Контекст, который задаёт все компромиссы: **домашний сервис, до пяти клиентов** (телевизор, ПК,
телефоны членов семьи). Изоляция важнее экономии ресурсов; каждый клиент по отдельности может вести
себя как угодно, и это не должно задевать остальных.

## 1. Целевая модель

```
клиент A ──┐                   ┌── пайплайн (A, файл 3) ──┐
клиент B ──┼── HTTP-сервер ────┼── пайплайн (B, файл 3) ──┼── торрент (один на hash)
клиент C ──┘   различает       └── пайплайн (C, файл 7) ──┘   ёмкость и бюджет
               клиентов                                        масштабируются
```

Три инварианта:

- **И-К (клиент).** HTTP-слой различает клиентов независимо от числа и порядка их запросов. Сколько
  бы запросов клиент ни открыл, он остаётся одним клиентом; два клиента никогда не выглядят как один.
- **И-П (пайплайн).** Ровно один GST-пайплайн на пару «клиент + видеофайл (+ аудиодорожка)». Действия
  одного клиента — перемотка, смена серии, отвал — не трогают чужой пайплайн.
- **И-Т (торрент).** Ровно одна закачка на torrent-hash, сколько бы клиентов её ни смотрели. Ёмкость
  кэша и бюджет соединений растут с числом активных читателей, а не делятся в ноль.

## 2. Что было в коде до внедрения — исторический раздел

> **Читать как историю, а не как текущее положение дел.** Этапы Э1–Э5 реализованы (коммиты
> `572b9755`, `5ad9ae58`, `2dd8da7a`, `903556cd`, `6bbbc96` в форке): HTTP различает клиентов через
> `?client=`, задача живёт на пару «клиент + файл + дорожка», ёмкость кэша и бюджет соединений
> масштабируются по числу активных читателей. Раздел сохранён, потому что он объясняет, **из чего**
> выросла целевая модель — три расхождения §3 читаются только вместе с ним. Что получилось на
> практике и что при этом сломалось, см.
> [`one-torrent-many-streams-concurrency.md`](one-torrent-many-streams-concurrency.md).

### HTTP-слой о клиентах не знал вообще

Все маршруты идентифицируют ресурс одним лишь хэшем
([handlers.go:20-29](../../external/TorrServer/server/gstreamer/handlers.go)):

```go
route.GET("/gst/:hash/master.m3u8", s.master)
route.GET("/gst/:hash/video.m3u8", s.videoPlaylist)
route.GET("/gst/:hash/init.mp4", s.initMP4)
route.GET("/gst/:hash/seg/*segment", s.segment)
route.GET("/gst/:hash/subs/*subtitle", s.subtitle)
```

и резолвят задачу как `s.Get(c.Param("hash"))` ([handlers.go:105, 323, 354, 392](../../external/TorrServer/server/gstreamer/handlers.go)).
Понятия «кто спрашивает» в коде нет ни в каком виде. Два телевизора и телефон для сервера
неразличимы.

### Задача — одна на торрент, а не на клиента

```go
tasks map[string]*Task   // service.go:44
...
id := hash               // service.go:172 — ключ карты это хэш, и только он
```

Отсюда всё остальное: `fileID` и `audio` хранятся **внутри** задачи, а запрос сегмента их не несёт,
поэтому `/gst/<hash>/seg/5.m4s` означает «пятый сегмент того файла, который сейчас лежит в слоте
этого торрента». Кто последним занял слот — тот и определяет, что получат все.

Это же порождает борьбу за слот, которую пришлось гасить отдельной машинерией: ограниченный цикл
попыток, ключ singleflight по тройке, `swapDefended` с grace-периодом
([разбор в 0007](gstreamer-pipeline-robustness.md)). Всё это — лечение симптома неверной
идентичности.

### Торрент один, но читателей сколько угодно, а ресурсы фиксированы

Торрент действительно один на хэш (`torr.GetTorrent(hash)`) — И-Т в этой части уже выполняется. Но:

**Ридер создаётся на каждый HTTP-запрос** и нигде не ограничен
([stream.go:84](../../external/TorrServer/server/torr/stream.go)):

```go
reader := t.NewReader(file)
defer t.CloseReader(reader)
http.ServeContent(resp, req, file.Path(), ..., reader)
```

**Бюджет соединений делится поровну** между всеми активными читателями
([cache.go:295](../../external/TorrServer/server/torr/storage/torrstor/cache.go)):

```go
count := settings.BTsets.ConnectionsLimit / len(readers)
```

При `ConnectionsLimit = 25` ([btsets.go:112](../../external/TorrServer/server/settings/btsets.go)) и
пяти читателях каждый получает пять соединений — включая тот, за которым сидит живой зритель.

**Ёмкость кэша фиксирована и одинакова для любого числа читателей.** Каждый торрент получает полный
`CacheSize` ([storage.go:36](../../external/TorrServer/server/torr/storage/torrstor/storage.go)):

```go
ch := NewCache(s.capacity, s)
```

по умолчанию 64 МБ ([btsets.go:108](../../external/TorrServer/server/settings/btsets.go)). При этом
вытеснение защищает куски, попавшие в диапазон **любого** читателя
([getRemPieces](../../external/TorrServer/server/torr/storage/torrstor/cache.go)), а освобождает
только то, что не защищено:

```go
// cleanPieces
if c.filled > c.capacity {
    rems := (c.filled-c.capacity)/c.pieceLength + 1
    ...
}
```

Если объединение диапазонов пяти читателей перерастает 64 МБ, освобождать становится нечего:
`remPieces` почти пуст, кэш переполняется, и куски, которые ещё нужны, вытесняют друг друга.

## 3. Три расхождения и что они дают на практике

| Уровень | Расхождение | Наблюдаемое следствие |
|---|---|---|
| Клиент | идентичности нет | нельзя ни изолировать, ни ограничить, ни диагностировать «кто именно чудит» |
| Пайплайн | ключ по хэшу | смена серии и второй клиент на той же раздаче вытесняют друг друга; лечится костылями |
| Торрент | ресурсы фиксированы, читатели нет | пять читателей по пять соединений; кэш на 64 МБ на всех; голодание пререлла |

Все три — один и тот же дефект на разных уровнях: **сущность, которую система обслуживает, не
совпадает с сущностью, которую она именует.** Обслуживается пара «клиент + файл», а именуется
торрент.

## 4. У-К: идентичность клиента

### Откуда берётся

Порядок предпочтения:

1. **Явный идентификатор устройства** — `?client=<id>` на `master.m3u8`. Плагин генерирует UUID один
   раз на устройство и хранит в `localStorage`. Это единственный надёжный источник: он переживает
   смену IP, не путает два приложения на одном устройстве и не ломается за NAT.
2. **Производный отпечаток** — когда `client` не передан: хэш от `RemoteAddr` + `User-Agent`.
   Достаточно для одного устройства на IP и не требует ничего от клиента.

**Сервер не должен доверять этому значению для безопасности.** Подделанный или совпавший
идентификатор означает ровно одно: два клиента разделят один пайплайн и будут мешать друг другу —
то есть деградируют до сегодняшнего поведения, но только между собой. На чужую изоляцию это не
влияет никак, потому что ключ задачи выводится из идентификатора, а не сверяется с ним.

### Идентичность — контракт оптимизации, а не предусловие

Соблазнительно сделать наличие идентификатора обязательным: «не сохранил сессию — не работаешь».
Так делать нельзя, и причина не техническая, а принципиальная. Живучесть не должна зависеть от
поведения клиента — это то же требование, из-за которого гейт читателей ставится в торрент-слое, а
не в плагине. Клиент, который не смог назваться, обязан получить рабочую деградацию, а не отказ.

Разделение простое:

- **живучесть** от клиента не зависит никогда;
- **качество изоляции** улучшается, когда клиент сотрудничает.

Назвался — свой пайплайн. Не назвался — производный отпечаток и, возможно, общий пайплайн с
соседом за тем же отпечатком. Хуже, но работает.

Практическое следствие: **деградация должна быть видимой**. Логировать, что клиент работает на
отпечатке вместо явного идентификатора, и отдельно — когда два независимых потока схлопнулись в
один отпечаток. Иначе «две вкладки мешают друг другу» будет выглядеть как загадочный баг
воспроизведения.

### Почему не cookie и не заголовок

Lampa отдаётся Plugin Hub'ом с порта 8095, TorrServer слушает 8090 — это **разные origin**. Cookie
поедет только при `withCredentials`, а ответ обязан нести конкретный origin: по спецификации Fetch
браузер отвергает credentials-запрос, если в ответе `Access-Control-Allow-Origin: *`. Сейчас стоит
именно звёздочка, а `AllowCredentials` не выставляется нигде
([server.go:74-77](../../external/TorrServer/server/web/server.go)). То есть понадобилась бы правка
общего CORS-middleware, который обслуживает и API, и WebDAV, и вызовы самого менеджера.

И всё это ради механизма, который не работает на главном устройстве: нативный плеер webOS тянет URL
медиапайплайном, а не XHR, и cookie там в лучшем случае непредсказуемы. Кастомный заголовок отпадает
по той же причине, плюс провоцирует preflight.

**Токен в пути перекрывает всё это и не требует от клиента хранилища вообще** — он живёт в URL,
которые сервер сам сгенерировал, а относительные `seg/N.m4s` и `init.mp4` плеер подставляет
механически. Сессию невозможно потерять, потому что её никто не держит.

| | токен в пути | cookie |
|---|---|---|
| Нужно хранилище у клиента | нет | да |
| Браузерный XHR | работает | `withCredentials` + правка CORS |
| Нативный плеер ТВ | работает | ненадёжно |
| Правки в общем middleware | нет | да |
| Видно в логах | да | нет |

Явный `?client=` остаётся полезным поверх токена, но по другой причине — см. следующий раздел.

### Где живёт в URL

Токен сессии — сегмент пути между хэшем и остальным:

```
/gst/<hash>/c/<token>/video.m3u8?audio=0
/gst/<hash>/c/<token>/init.mp4?audio=0&seconds=0
/gst/<hash>/c/<token>/seg/5.m4s
/gst/<hash>/c/<token>/subs/1/5.vtt
```

Почему именно путь, а не query (про cookie — разобрано выше):

- **`seg/N.m4s` и `init.mp4` в плейлисте — относительные**
  ([handlers.go:291, 312](../../external/TorrServer/server/gstreamer/handlers.go)), они разрешаются
  относительно расположения `video.m3u8`. Токен в пути подхватывается ими **автоматически**, менять
  генерацию этих строк не нужно.
- Абсолютных URL, которые сервер пишет сам, всего два — `video.m3u8` и `subs/*.m3u8`
  ([handlers.go:135, 205](../../external/TorrServer/server/gstreamer/handlers.go)). Правка
  локальна.
- Query отпадает ровно поэтому же: относительные `seg/N.m4s` строку запроса не наследуют.

### Как вычисляется

Токен **детерминированный**, а не случайный:

```
token = hex(sha256(clientID ‖ 0x00 ‖ hash ‖ 0x00 ‖ fileID ‖ 0x00 ‖ audio))[:16]
```

Это существенно: hls.js перезапрашивает `master.m3u8` при ошибках и переинициализации. Случайный
токен на каждый запрос породил бы новый пайплайн на каждую перезагрузку плейлиста — ровно та
болезнь, которую лечим. Детерминированный означает: тот же клиент, тот же файл, та же дорожка → тот
же токен → тот же пайплайн.

**Хэш входит в токен**, хотя URL и так его несёт отдельно. Причина не в адресации, а в том, что
токен — единственный ключ карты задач: `fileID` — это индекс файла внутри раздачи, поэтому файл 3
двух разных раздач без хэша дал бы один и тот же ключ и одну задачу на два разных видео. Проверка
`task.Hash == hash` при резолве от этого не спасает — коллизия происходит раньше, при вставке.

### Что чинит явный `client`, а токен сам по себе не чинит

Токен наследует качество `clientID`. Пока тот выводится из отпечатка `RemoteAddr` + `User-Agent`,
остаются два реальных случая:

- **Две вкладки или два приложения на одном устройстве**, играющие один файл, дают одинаковый
  отпечаток → один токен → общий пайплайн → взаимные помехи. Ровно тот дефект, который вся работа
  устраняет, — но между вкладками одного устройства.
- **Смена адреса** (перезаезд DHCP, переход Wi-Fi → Ethernet) меняет отпечаток → новый токен →
  новый пайплайн, а прежний висит до таймаута неактивности.

Оба закрываются явным `?client=`. Но **одного `localStorage` для этого мало**, и это важнее, чем
кажется на первый взгляд: `localStorage` общий для всех вкладок одного origin, поэтому UUID оттуда —
это идентичность браузерного профиля, а не вкладки. Две вкладки получили бы один и тот же явный
`client` и слились бы в один пайплайн ровно так же, как сливались на отпечатке. Первый случай
остался бы незакрытым.

Поэтому идентификатор состоит из двух половин:

```
client = <device>.<consumer>
```

- **device** — постоянный, живёт в `Lampa.Storage`. Он переживает перезапуск приложения и смену
  адреса, то есть закрывает второй случай.
- **consumer** — живёт в `sessionStorage`, который приватен для вкладки и переживает перезагрузку
  страницы. Он закрывает первый случай.

Что при этом теряется: новая вкладка и перезапуск приложения дают новый `consumer`, то есть прежняя
сессия остаётся висеть до подчистки по неактивности. Это правильный размен — перезапуск приложения
действительно означает нового потребителя, а брошенную сессию подберёт вытеснение по лимиту.
Обратный размен (постоянный `consumer`) вернул бы слипание вкладок, которое и лечим.

Отсутствие `client` при этом остаётся допустимым: клиент без него играет на отпечатке. Никакой
принудиловки — см. «Идентичность — контракт оптимизации, а не предусловие» выше.

## 5. У-П: пайплайн на клиента и файл

### Ключ

`Service.tasks` меняет ключ со строки-хэша на токен сессии:

```go
tasks map[string]*Task    // ключ — token, а не hash
```

`fileID` и `audio` перестают быть «состоянием слота» и становятся частью идентичности. Запрос
сегмента больше не должен угадывать, что лежит в слоте: токен однозначно указывает на задачу.

`s.Get(hash)` во всех обработчиках заменяется на `s.GetSession(token)`; `hash` остаётся в пути для
торрент-слоя и диагностики.

### Что при этом исчезает

Механизмы из 0007, введённые против борьбы за слот, становятся не нужны, потому что борьбы больше
нет:

- `swapDefended` и `taskSwapGrace` — вытеснять нечего, у каждого клиента свой слот;
- ограниченный цикл попыток в `GetOrAdd` с `ErrTaskBusy` — конкурировать не за что;
- ключ singleflight по тройке — тройка и есть ключ задачи.

Их следует **удалить, а не оставить на всякий случай**: они маскируют поведение и усложняют
рассуждение о новой модели. Гейт по хэшу торрента из 0011 (`acquireTorrent`), наоборот,
**сохраняется** — он про И-Т, а не про И-П, и остаётся нужен.

### Цена

Два клиента, смотрящие один файл, получают **два** пайплайна. Это осознанный размен: изоляция
дороже, но общий пайплайн означает, что перемотка одного дёргает картинку другому — сегодняшний баг.
При пяти клиентах это до пяти пайплайнов: порядка 0.5–1 ГБ памяти и пять читателей на торрент.
Для домашнего сценария приемлемо; при желании экономить — см. §9.

## 6. У-Т: один торрент, растущие ресурсы

### Ёмкость кэша

`Cache.capacity` уже мутабельна (`AdjustRA` меняет её на лету), значит масштабирование возможно без
переделки хранилища:

```
capacity = CacheSize × clamp(активных читателей, 1, N) , с потолком по доступной памяти
```

Смысл — не «дать больше на всякий случай», а сохранить условие, при котором вытеснение вообще
работает: объединение диапазонов читателей должно помещаться в ёмкость, иначе `remPieces` пуст и
кэш захлёбывается.

Пересчитывать при появлении и уходе читателя.

### Бюджет соединений

Плоское деление заменяется полом на читателя:

```go
count := max(minPerReader, settings.BTsets.ConnectionsLimit / len(readers))
```

Пять соединений на живого зрителя — это голодание. Пол (порядка 8–10) гарантирует, что добавление
фонового читателя не роняет воспроизведение. Побочно это означает, что суммарный бюджет может
превысить `ConnectionsLimit` — так и надо: `EstablishedConnsPerTorrent`
([btserver.go:121](../../external/TorrServer/server/torr/btserver.go)) задаётся один раз при старте
и в домашнем сценарии его следует поднимать вместе с числом клиентов.

### Ограничение числа читателей

Клиент, открывший пятьдесят range-запросов, сегодня создаёт пятьдесят читателей. Лимит должен
стоять в `torrstor.Cache.NewReader` — **не в gstreamer**, потому что через `/stream` ходят и DLNA, и
WebDAV, и прямое скачивание, и предзагрузка. Это и есть требование «сервер справляется сам,
независимо от клиента».

Сверх лимита — отказ с `503` и `Retry-After`, а не постановка в очередь: очередь удерживает
HTTP-соединения и лишь переносит проблему.

## 7. Живучесть при неадекватном клиенте

| Поведение клиента | Защита | Уровень | Состояние |
|---|---|---|---|
| Оборвал соединение на середине сегмента | запись вне гейта задачи + дедлайн | пайплайн | есть (0003) |
| Шторм повторов одного сегмента | дебоунс по (сегмент, дорожка) | пайплайн | есть (0012) |
| Скраб по таймлайну | гейт с учётом контекста | пайплайн | есть (0002) |
| Не читает тело ответа | дедлайн записи | пайплайн | есть (0003) |
| Смена серии на лету | своя задача на файл | **пайплайн** | **нужно (У-П)** |
| Второй клиент на той же раздаче | своя задача на клиента | **пайплайн** | **нужно (У-П)** |
| Десятки параллельных соединений | лимит читателей на торрент | **торрент** | **нужно (У-Т)** |
| Фоновая предзагрузка мешает просмотру | пол бюджета + масштаб ёмкости | **торрент** | **нужно (У-Т)** |
| Подделал `client` | деградация только для себя | клиент | следует из У-К |

## 8. Порядок внедрения

Каждый этап самостоятелен и оставляет систему рабочей.

**Э1. Идентичность клиента, без смены поведения.** Ввести вычисление `clientID` и токена, добавить
маршруты с `/c/<token>/`, оставив старые как есть. Логировать клиента в GST-ошибках. На этом этапе
задача по-прежнему одна на хэш — меняется только наблюдаемость. Сразу даёт ответ на вопрос «кто
именно чудит», которого сегодня нет.

**Э2. Ключ задачи — токен.** Перевести `tasks` на токен, `s.Get` → `s.GetSession`, обновить два
абсолютных URL в плейлистах. Удалить `swapDefended`, `taskSwapGrace`, `ErrTaskBusy`-цикл. Старые
маршруты без `/c/` перевести на производный отпечаток, чтобы ничего не сломалось у клиентов, которые
их ещё зовут.

**Э3. Лимит читателей на торрент.** В `torrstor.Cache.NewReader`. Самостоятельная ценность:
защищает и от не-GST путей.

**Э4. Масштабирование ёмкости и пол бюджета.** Правки в `cache.go`. Делать последними: их эффект
измеряется только под реальной многоклиентской нагрузкой, а до Э2 её толком не воспроизвести.

**Э5. Плагин.** Генерация и хранение `clientID`, добавление `?client=` к `master.m3u8`. Отдельно и
последним: до Э1 это ни на что не влияет, а после Э1 работает и без него через отпечаток.

## 9. Границы и что не делается

- **Общий пайплайн для клиентов на одном файле** не делается сознательно: он вернул бы взаимное
  влияние перемоток. Если память станет проблемой — правильный размен не «делить пайплайн», а
  ограничить число одновременных пайплайнов (`MaxTasks`, сегодня по умолчанию `0` = без лимита) и
  отдавать `503` сверх него.
- **Авторизация и разграничение доступа** не рассматриваются: идентификатор клиента здесь нужен для
  изоляции ресурсов, а не для прав.
- **Раздельные аудиодорожки одного файла** остаются разными задачами (дорожка входит в токен). Это
  дороже, но переключение дорожки и так требует перезапуска пайплайна.
- **Схема URL меняется** — это внешне наблюдаемое изменение. Старые пути обязаны продолжать
  работать до Э5, иначе обновление сервера ломает уже запущенные плееры.

## 10. Что проверить

Ни один из пунктов не закрывается юнит-тестами полностью — модель про одновременность и реальные
данные.

- Два клиента, одна раздача, **разные** файлы: оба играют, ни один не вытесняет другого (сегодня —
  вытесняют).
- Два клиента, один файл: независимая перемотка, скраб одного не трогает картинку у другого.
- Пять клиентов на одной раздаче: измерить фактическую скорость на каждом и заполнение кэша; на этом
  сценарии проверяются У-Т целиком.
- Клиент открывает 50 параллельных запросов: сервер отвечает `503` сверх лимита, остальные клиенты
  не деградируют.
- Перезагрузка `master.m3u8` тем же клиентом: пайплайн **не** пересоздаётся (проверка
  детерминированности токена).
- Прогон под `-race` после каждого этапа: модель идентичности трогает разделяемое состояние.
